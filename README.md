# <img src="web/public/favicon.svg" width="32" height="32" alt="" /> Gond Agent

Self-hosted coding agents that turn repository tasks into pull requests. Every account has every feature: all configured models, scheduled runs, pull requests, images and profile photos.

## Images in replies

Images shared in replies appear as captioned cards on the run page, with click or
keyboard enlargement. Use `share_image {path, caption?}` for screenshots or other
raster files anywhere under the workspace or `/tmp`, including browser screenshots
and other tool outputs. Any readable regular raster image in those locations can
be shared; non-images and SVG are rejected. Symlinked workspace or `/tmp` roots
are resolved canonically; `TMPDIR` does not grant access to another location.
Local Markdown paths cannot be served
and now show “image not available (local path)”. Absolute same-origin HTTP(S) URLs
render only for static app assets under `/agents/` and saved run images matching
`^/api/v1/runs/[A-Za-z0-9_-]+/images/[A-Za-z0-9_-]+$`, after URL normalization.
Credentials, percent encoding, backslashes, query strings and fragments (including
empty delimiters) are rejected. Other HTTP(S) Markdown images remain links, never
automatic requests; data/blob previews still render. Shared images survive workspace release and
follow the run's owner-only access and retention rules. Limits: four sharing
attempts per execution turn, 32 saved images / 16 MiB per run; 20 MiB input,
1568px longest side and 1 MiB normalized JPEG/PNG output per image. No new
network access or dependencies are needed. Both worker and service strip caption
control/format characters (including bidi controls and ZWJ/ZWNJ), tags and variation
selectors, with a 1000-character input cap. The service checks PNG/JPEG signatures
against the declared type; image responses use `private, no-store`, `nosniff` and a
`sandbox` CSP. Submission is not confirmation: the service may decline at a cap,
in which case the person sees “Image sharing limit reached” and the image is not saved.

## Connect an external agent with MCP

Open **Settings → Agent access → MCP access**, name a token, and copy it when it is created. Tokens expire after 90 days and can manage all sessions owned by their account, including browser-created runs. Revoke tokens from the same section; revocation does not stop existing runs.

Retry records remain available for the token's entire valid lifetime. Expired/revoked token history is removed after 30 days; invalid-token retry records are cleaned up by the scheduler.

Configure an MCP client that supports authorization headers:

```json
{
  "mcpServers": {
    "gond": {
      "type": "http",
      "url": "https://agent.example.com/mcp",
      "headers": { "Authorization": "Bearer YOUR_TOKEN" }
    }
  }
}
```

Forward `/mcp` through your existing HTTPS reverse proxy, preserving authorization headers and allowing responses to wait at least 30 seconds. Configuration syntax varies by client. OAuth-only connectors are not supported. Keep tokens out of source control and shared configuration.

Agents can discover repositories and models, start sessions, read progress and diffs, send follow-ups, stop work, and open pull requests. They use the token owner's model access, including their ChatGPT plan sign-ins. Start with an explicit model ID from `list_models`. Use a unique `request_id` for each start or follow-up, reusing it only to retry identical arguments. Session output is untrusted content. Direct worker shell/file tools, merges, credential management, and image uploads are excluded. See [the protocol](protocol/README.md#remote-mcp) for tool contracts.

`start_session` accepts optional `title`, `branch` and `pr_body`, also supported by workspace run creation. A title is plain text without newlines, at most 120 characters, and supplies the run, commit and PR titles. A custom branch must match `^(gond-agent|feat|fix|chore|docs)/[a-z0-9][a-z0-9._-]{0,80}(/[a-z0-9._-]{1,80}){0,3}$`, with no `..`, trailing slash or `.lock` suffix; protected names `main`, `master`, `HEAD`, `release*` and `v*` are refused. An existing remote branch is refused unless it belongs to this run.

`pr_body` is plain text up to 20,000 characters. Set it on start or override it with `send_session_message` (or a workspace follow-up); the override persists. An explicit body supplies the prose even when empty. Otherwise, the PR uses clean main-agent final text after the last tool call, falling back to the plain run title, never the prompt. The shared `descriptionFor` policy neutralizes caller/model Verification headings and markers and always appends a service-generated **Verification** block, including when the gate is off or no records exist. Only `end_turn` (the runner's normalized clean stop) qualifies; truncated, refusal/filter and unknown stops do not. Failed/stopped runs and successful turns with no final text use the title. Commentary and subagent text are excluded; the live event transcript stays unchanged.

## Home run history

Home loads one server-paginated page at a time. **Rows per page** offers 10, 25 (default), 50 and 100, with Previous/Next and an inclusive range below the list. The browser remembers the size (`gond-agent.runs-page-size`) before the first render. `?page=3&size=25` overrides that preference; `tab=all|working|ready|merged` and `repo=owner/name` preserve filters on refresh. Changing a tab, repository or size returns to page 1. Invalid page/size values use 1/25; pages beyond the history clamp to the last page.

Refreshes keep the current page number and update counts. New runs shift the newest-first window; finishing runs can leave a filtered tab. Only a page that no longer exists moves backward. Tab totals cover the whole selected repository, not just the visible page. Working includes queued runs. The sidebar/search retains its independent, bounded recent history.

The authenticated `GET /api/v1/runs` endpoint accepts `limit` (1–100, default **100** for existing callers), `offset` (default 0), `tab` and `repo`. Results retain `runs` and queue/capacity fields, adding `total`, normalized `limit`/`offset`, `start`/`end`, `counts` and the account's `repositories`. Order is `created_at DESC, id DESC`. See [the HTTP contract](protocol/README.md#workspace-run-pagination). MCP `list_sessions` is unchanged: numeric offset `cursor=0`, `limit=30` by default (1–100), and nullable `next_cursor`, in the same stable order; it does not inherit Home filters or size.

For local UI verification, build `web/`, then run `node api/test/home-pagination.local.cjs /tmp/home-pagination` with Playwright available through `NODE_PATH` and its Chromium install through `PLAYWRIGHT_BROWSERS_PATH`. This starts a disposable HTTP service, mocks the history, and captures the 65-run fixture in both themes at 1440 and 390 px. Large diff counts exercise the compact desktop tiles and mobile counts, checking exact-count tooltips and that text and diff squares stay inside their tiles or rows. The same browser assertions run during packaged onboarding in CI; real SQLite list responses are covered by `api/test/run-pagination.test.ts`.

## Run on your server

Requirements: a Linux x86_64 host with a current Docker Engine (25+) and Docker Compose, plus at least 2 GiB RAM and disk space per active run. A normal Linux VM on Proxmox works without nested virtualization. The application runs in Docker and creates one separate non-root worker container per run.

The Compose configuration is [docker-compose.yml](docker-compose.yml); supported deployment settings are documented in [.env.example](.env.example). It uses prebuilt runtime and worker images from GHCR. You do not need to build the source on your server.

```sh
cp .env.example .env
openssl rand -base64 32
# Paste the output into BETTER_AUTH_SECRET in .env; set your browser origin.
chmod 600 .env
docker compose config --quiet
docker compose pull
docker compose up -d
```

Use `docker compose config --quiet` to validate without printing resolved secrets. Keep the auth secret stable across upgrades because it protects sessions and encrypted connections. `PORT` selects the published host port; update `BETTER_AUTH_URL` to match the browser origin. `DOCKER_SOCKET_PATH` selects the existing Docker socket. A missing socket causes a startup error instead of being silently created. The named `gond-agent-data` volume persists SQLite and run data; do not remove it during upgrades.

1. Copy `.env.example` to `.env`. Set `BETTER_AUTH_SECRET` (generate with `openssl rand -base64 32`) and `BETTER_AUTH_URL`. Keep this secret unchanged across restarts.
2. Run `docker compose pull`, then `docker compose up -d`. Both images are pulled. The `worker-image` helper exits successfully without starting an agent; this is expected. The API creates disposable workers from that image when runs start. Open `http://localhost:8787`. Create the first account while bound to loopback; that account becomes the administrator. Complete model setup in the browser. All accounts have all features; additional registration is disabled unless `ALLOW_SIGNUP=true`.
3. Open **Plugins → GitHub → Connect GitHub**. Copy the one-time code and follow **Continue on GitHub** to approve it. The runtime already includes GitHub CLI; no download, host login or credential-directory mount is required. Each workspace account connects its own GitHub account; its runs use that account’s repository access.
4. For remote access, put an HTTPS reverse proxy in front, set `BETTER_AUTH_URL` to the public origin, and restart. Forward WebSocket upgrades for `/ws/` and preserve the origin. Enable `TRUST_PROXY=true` only when the proxy overwrites `X-Forwarded-For`; otherwise rate limits use the direct peer address. Set `BIND_ADDRESS` only as needed. Create the first account before exposing the instance.

Open the server root `/` to enter the application at `/agents/`. An empty instance opens administrator account creation, followed by model-provider setup. Existing instances open sign-in or the workspace. The container contains no marketing frontend. The public product homepage is [gond.io/agent](https://gond.io/agent), maintained separately in `gond-landing`. Health is at `/health`; auth routes are at `/api/auth/`. CI publishes `ghcr.io/dawsja/gond-agent` and `ghcr.io/dawsja/gond-agent-worker`; `main`, version and SHA tags are available after their workflows succeed. Private packages require registry authentication.

### GitHub connection

Every account can connect, reconnect or disconnect its own GitHub in **Plugins → GitHub**. The login and numeric-ID noreply address of the run owner's effective GitHub connection are used for commits and pull requests. Repository and branch lists use the signed-in account; MCP requests use the personal token owner; schedules use the schedule owner. Without credentials, runs return “Connect your GitHub account in Plugins > GitHub”.

The device code is visible only to the initiating signed-in session; separate accounts can connect concurrently. Codes expire after ten minutes. Approve only the code shown in your own workspace. GitHub CLI requests its standard scopes plus workflow access. Organization SSO or OAuth restrictions may require additional approval on GitHub.

The administrator's shared-connection option in Plugins → GitHub is an on/off switch. It saves immediately, is unavailable while saving and restores the previous value if saving fails. Other boolean settings use the same switch; single sign-on configuration still requires **Save sign-in settings**.

GitHub connection controls live only in **Plugins → GitHub** (`/agents/plugins/github`). Old Settings Connections bookmarks redirect there; Settings keeps model connections under Models and account linking under Account.

Approved credentials are encrypted in SQLite with `BETTER_AUTH_SECRET`. Temporary private CLI authorization files are removed on completion, cancellation, expiry and startup. API calls, clones, pushes and PR operations use command-scoped credentials; tokens never reach browsers, repository archives or workers. **Reconnect GitHub** replaces a credential only after approval. **Disconnect** deletes the saved personal token and cancels pending authorization; deleting the local account also deletes its connection. These actions do not revoke GitHub's OAuth grant: use GitHub's **Settings → Applications → Authorized OAuth Apps** to revoke that grant upstream.

Administrators additionally see **Shared connection**, for accounts without their own GitHub connection, and **Use the shared GitHub connection for accounts without their own**. They can connect/replace/disconnect the shared credential and toggle fallback, but cannot view another account's personal token or repositories. The fallback is **off on new installs without saved shared or service credentials**. On upgrade, an existing shared credential, a non-empty service-side `GH_TOKEN`/`GITHUB_TOKEN`, or `GH_CONFIG_DIR` containing a non-empty `hosts.yml` enables fallback once, preserving existing runs and owners; an administrator's later choice survives restarts. Personal credentials always win. Resolution is personal → shared (only when fallback is enabled) → explicit service-side `GH_TOKEN`, `GITHUB_TOKEN` or `GH_CONFIG_DIR` credentials (also only when fallback is enabled) → a connection error. Turning fallback off prevents every account without a personal connection from using either shared or service credentials. The fallback switch covers both the saved shared connection and service credentials; keep it off for strict account-only access. Default Compose does not mount host GitHub configuration or set an empty `GH_CONFIG_DIR`; configure service credentials explicitly if needed.

### Administrator roles and OIDC linking

The first registered account is an administrator. An administrator can use **Settings → Sign-in & people → People** to promote or demote accounts, including OIDC accounts. At least one administrator must remain. This changes operational permissions only; it does not merge accounts, run history or personal connections.

To add single sign-on to an existing account, sign in to that account, then within ten minutes choose **Settings → Account → Sign-in methods → Link <provider name>**. Complete the provider's authorization. Better Auth requires the identity provider to supply a verified email or to be configured as a trusted provider; otherwise linking is refused. The verified ID token subject identifies the linked identity; matching email addresses never link accounts implicitly. Unlink is offered only when another sign-in method remains. New OIDC account creation continues to follow `ALLOW_SIGNUP`.

If you already have an administrator password account and a separate non-admin OIDC account, sign in with the password and promote the OIDC account under **People**. Alternatively, use **Link <provider name>** from the administrator account if the identity is not already attached elsewhere. An identity already linked to another account is refused: promote that account, or (if it has another sign-in method) sign in there and unlink first. There is no automatic account merge.

The account popup at the bottom of the sidebar contains Settings and Sign out; Settings is not a sidebar navigation item. The Settings Account card shows your photo, name and email. Sign out stays in the account popup; Settings omits the instance label and storage information block. Collapsed navigation uses tooltips; hover or focus the logo to expand it.

In **Settings → Appearance**, choose **System**, **Light** or **Dark**. System is the default and follows your device live. The preference belongs to your account and follows you to other devices; a local copy only paints the first frame before the server responds. Light uses Gond's linen, paper and carbon palette; Dark preserves Gond Code's existing dark blue palette. The neighboring **Color** control offers blue, purple, pink, red, orange, amber or green in either scheme. The accent is also saved to your account; branding, status colors and neutral avatars stay unchanged. The sidebar shows the logo alone, at the same readable size when expanded or collapsed. In either message composer, **Enter sends** and **Shift+Enter adds a newline**; IME composition does not submit. Your account shows a neutral grey default picture. Pictures from your sign-in provider are never used or loaded; upload your own photo in Settings, Account. In **Settings → Account**, upload a PNG, JPEG or WebP profile photo (up to 2 MiB and 16 megapixels), reposition/zoom it in a circular preview and save. Photos appear in the account menu and your messages, survive restarts, and can be changed or removed. The server re-encodes them as metadata-free, circular 256px PNGs in SQLite. Photos require an authenticated session to view and only their owner can replace or remove them.

In a run's conversation, scrolling up reveals a square down-arrow above the composer. **Scroll to bottom** smoothly returns to the newest content and resumes following updates; reading earlier messages pauses following. The control stays above growing drafts and attachments and respects reduced motion.

Remote images in rendered Markdown output are shown as links (using their alt text or URL) and never loaded automatically. Same-origin images use the path allow-list described in **Images in replies**, not arbitrary API routes; data/blob image previews still work. An image Content-Security-Policy (`img-src` only) also blocks remote image requests, including tracking pixels and exfiltration beacons; it does not restrict scripts, frames or other resources.

The sidebar uses a compact 28px logo in a 48px header: aligned with navigation icons when expanded, centered when collapsed. **Settings → Danger zone → Delete account** permanently removes your local account, sessions, photos, schedules, runs, images and usage records. Search opens that section, not a deletion action. An extra confirmation asks for your email and current password; passwordless accounts require a sign-in within the last 15 minutes. Stop active runs before deleting. You cannot delete the only administrator while other accounts remain. Deleting the final account also clears saved provider, GitHub and single sign-on connections and returns the server to administrator registration and model setup, even when general registration is closed. Work pushed to GitHub is not deleted.

### Updates

After the initial setup, update both images and recreate the changed services with:

```sh
docker compose pull
docker compose up -d
```

Keep your data volume and `BETTER_AUTH_SECRET`. Do not use `down -v`. Updating the service interrupts active runs; usable checkpoints preserve the last completed round for recovery. Eligible browser/MCP runs resume automatically by default; you can also resume or send a follow-up. Without a usable checkpoint, follow-ups start from the last pushed branch. To pin a release, set the same version tag in both `GOND_AGENT_IMAGE` and `GOND_AGENT_WORKER_IMAGE`.

```sh
GOND_AGENT_IMAGE=ghcr.io/dawsja/gond-agent:0.1.0
GOND_AGENT_WORKER_IMAGE=ghcr.io/dawsja/gond-agent-worker:0.1.0
```

The image tag has no `v` (use `0.1.0`, not `v0.1.0`), and both variables must use the same version.

If your `.env` selects `:local` images, change both entries to the GHCR images in `.env.example` to use this pull-only flow.

### Optional source builds

For development or an unpublished change, explicitly add the build override:

docker compose -f docker-compose.yml -f docker-compose.build.yml build

### Container security and limits

Docker socket access gives the Gond Agent service administrative control of the Docker host. Use a dedicated trusted machine or Linux VM; do not expose the socket over unauthenticated TCP. Worker containers never receive the socket, application data, host bind mounts, GitHub credentials or provider keys. They run as UID 1000 with a read-only root, dropped capabilities, no privilege escalation, a PID limit, and private workspace volumes/networks. `RUN_CPUS` and `RUN_MEMORY_MB` default to 2 and 2048; `MAX_ACTIVE_RUNS` defaults to 5. Workspace disk use is not quota-limited: monitor free disk space.

Workers keep `/tmp` (1 GiB) and `$HOME` (256 MiB) on `nosuid,nodev,noexec` tmpfs. Install executable toolchains in `/opt/gond-tools`, a second writable, executable named volume owned by UID 1000 outside the Git checkout. Each run has its own tools volume, with the same instance/run labels and cleanup as the workspace: close, destroy, failed startup and restart recovery remove it. Follow-ups in a live run retain it; reopening a closed run starts fresh. Nothing is shared across runs or users: a shared executable cache could let one run poison another. Workspace **and tools** disk use is not quota-limited; monitor Docker host storage, especially for Rust installations.

Installer scratch (`TMPDIR`, `TMP`, `TEMP`, `TEMPDIR`) uses `/opt/gond-tools/tmp`, created in the image with UID 1000 ownership and recreated defensively before the worker starts. Installers can execute temporary binaries there without making `/tmp` or home executable. `XDG_CACHE_HOME=/opt/gond-tools/cache`, `BUN_INSTALL_CACHE_DIR=.../cache/bun`, `npm_config_cache=.../cache/npm`, `PIP_CACHE_DIR=.../cache/pip` and `UV_CACHE_DIR=.../cache/uv` keep caches off the 256 MiB home tmpfs and clean them with the tools volume. `CARGO_TARGET_DIR` is not set globally or for ordinary workspace commands, so Cargo keeps its normal target selection. Only Rust LSP children use `/opt/gond-tools/target` (`RUST_TARGET_DIR` in the runner).

The image ships Node/npm, Corepack, Python/pip, Bun 1.4.4, uv 0.9.7 and Playwright/Chromium. Bun and uv are pinned linux/amd64 official release assets verified with SHA-256 before installation. Installer variables (`BUN_INSTALL`, `CARGO_HOME`, `RUSTUP_HOME`, `UV_INSTALL_DIR`, `UV_TOOL_DIR`, `UV_PYTHON_INSTALL_DIR`, `UV_TOOL_BIN_DIR`, `XDG_BIN_HOME`, `XDG_DATA_HOME`, `PYTHONUSERBASE`, `npm_config_prefix`, `COREPACK_HOME`, `PNPM_HOME`) point into the tools volume; its bin directories (including `/opt/gond-tools/python/bin` for `pip install --user`) follow the image PATH so downloaded tools cannot shadow image commands such as Git, Python or Bash. uv tool environments and managed Python installations also live in the executable tools volume, not noexec home. Playwright and Node retain their explicit image browser/module paths. The fixed Bun pin supports `bun.lock` lockfileVersion 2; repository `packageManager` fields do not automatically switch Bun versions. Rust is installed per run, for example:

```sh
curl --proto '=https' --tlsv1.2 -sSf https://sh.rustup.rs | sh -s -- -y --profile minimal -c rustfmt -c clippy
cargo --version
```

Noexec scratch is defense in depth against dropped binaries, not the isolation boundary: Python, Node and Bash already execute arbitrary code as UID 1000, including syscalls through FFI. The boundary remains the container: dropped capabilities, no-new-privileges, default seccomp, read-only root, private volumes/network, and no host mounts, Docker socket or credentials. Executing downloaded/compiled native code exposes more of the kernel's seccomp-filtered syscall surface. Docker's ordinary disk-backed named-volume interface does not offer per-mount `nosuid,nodev`; these flags remain enforced on scratch tmpfs, not claimed for the tools volume. Dropped capabilities and no-new-privileges still prevent privilege gains via devices or setuid binaries. The existing checkout volume is also executable; do not install toolchains there because they would pollute snapshots.

To bake Rust or other large dependencies into an operator-controlled custom image, extend the worker image (not the runtime), install into the read-only image's `/usr/local` rather than the per-run volume, and restore UID 1000:

```dockerfile
FROM ghcr.io/dawsja/gond-agent-worker:main
USER root
# Install pinned project-specific dependencies into /usr/local here.
USER 1000:1000
```

Build it with `docker build --platform linux/amd64 -t gond-agent-worker:custom -f Dockerfile.worker .`, set `GOND_AGENT_WORKER_IMAGE=gond-agent-worker:custom` in `.env`, and run `docker compose up -d --pull never`. Both the helper and service select that image; it must exist on the service's Docker host. Per-repository setup settings and shared toolchain caches are not supported.

Containers share the host kernel and are not a boundary for hostile multi-tenant workloads. Their bridge networks allow dependency downloads; host/LAN destinations are not automatically blocked, so apply host firewall/egress policies when needed. Chromium uses the container as its containment boundary and runs without its own sandbox. Keep the host kernel, Docker and worker image updated.

## Authentication and OIDC

Open **Settings** from the profile menu. Settings has topic pages with a left navigation on desktop and a page selector on phones:

- **Account** (`/agents/settings/account`): photo, name/email, sign-in methods and active sessions.
- **Appearance** (`/agents/settings/appearance`): theme and personal color.
- **Models** (`/agents/settings/models`): ChatGPT plan, followed by administrator-managed API providers.
- **Agent access** (`/agents/settings/agent-access`): administrator-managed Web search and your MCP tokens.
- **Sign-in & people** (`/agents/settings/sign-in-people`): administrator-only single sign-on and account roles.
- **Danger zone** (`/agents/settings/danger-zone#delete`): account deletion, with its existing confirmation steps.

`/agents/settings` opens Account. Existing section hashes, category hashes and `section`/`tab`/`anchor` query bookmarks redirect to the matching page and section; old Connections/GitHub bookmarks still open Plugins → GitHub. Sidebar search opens the matching page **and section**, without performing an action. Administrator-only items are absent from member navigation and search. Draft edits, expanded details and scroll positions stay in memory while switching Settings pages (including Back/Forward); they are not saved automatically and are cleared by a reload or leaving Settings. No secret drafts are stored in browser storage. Usage and Automations remain workspace pages; GitHub remains in Plugins. There are no separate Notifications or About settings in this workspace.

Better Auth handles email/password sign-up, password hashing, cookies, sessions, CSRF checks and rate limiting. Passwords need at least 12 characters. Settings lists and revokes active sessions. An administrator can configure an OIDC issuer, client ID and secret in Settings; the page shows the redirect URI to register with the provider. Discovery, PKCE and verified ID tokens are required. Password sign-in remains enabled. OIDC changes require a sign-in within the last ten minutes. Client secrets are encrypted in SQLite and never returned to the browser. Set `ALLOW_SIGNUP=true` to permit new users, including new OIDC users. Account linking by matching emails is disabled. The provider’s `picture` claim is ignored; only locally uploaded account photos are shown.

## Model providers

Every run uses Gond Agent's built-in runner. Models come from two places: API connections an administrator saves for everyone, and ChatGPT plans that each account signs in to for itself (see [ChatGPT plan](#chatgpt-plan)). Model pickers show versioned names from provider catalogs, without a hardcoded version list. Hover a model to see its exact reported ID, or search by that ID.

A ChatGPT sign-in works without an API provider. To remove unused API connections, open **Settings → Models → Model providers → Advanced settings → Remove provider**, then **Save changes**. You can remove the final API connection. Connection warnings appear only for the selected connection, or when no models are available.

New tasks and follow-ups place image attachments first, then the model and thinking effort selectors. Model and thinking menus share the same style and control height and show each model's brand mark. Follow-ups can switch to any available model, including between API connections and a ChatGPT plan.

After the first sign-in, setup offers **Continue with ChatGPT** and a ready-to-edit API connection. An administrator can add more connections in **Settings → Models → Model providers**, directly below **ChatGPT plan**. Choose **OpenAI** (including compatible APIs) or **Anthropic**, add a key if required, then save. Provider URLs are filled in automatically; **Edit URL** allows a custom API base URL including its prefix, such as `http://127.0.0.1:8000/v1`. Setup does not require selecting or entering models. Connection names are optional overrides under **Advanced settings**. OpenAI connections default to Chat Completions; select Responses there if your provider requires it. Saved protocol choices are preserved.

When starting an agent, the model picker automatically combines available models from every saved connection, grouped by connection name. Adding another key/URL expands these choices without a separate model-configuration step. Identical model IDs from different connections remain separate options, so the selected connection supplies the correct key. **Refresh models** reloads the catalog. Auto uses the saved instance default when available, otherwise the first available model. New instances do not need to configure a default.

Supported API formats are OpenAI Responses, OpenAI Chat Completions and Anthropic Messages. Any OpenAI-compatible endpoint works with the OpenAI button, including xAI (`https://api.x.ai/v1`, Responses or Chat Completions) and proxies such as LiteLLM, OpenRouter, vLLM or Ollama. Each format supports model discovery, streamed text and tool calls, images where the model accepts them, token and cache usage, and plain error messages. Thinking effort is sent the way each provider expects: Responses `reasoning.effort` (xAI without reasoning summaries), Chat Completions `reasoning_effort`, and Anthropic adaptive effort or a thinking budget. Grok accepts an effort only on its mini reasoning models; other Grok models reason without one. Official OpenAI and xAI catalogs hide embedding, audio, image-generation and moderation models that can't run the agent.

Selecting Anthropic switches the built-in OpenAI URL to `https://api.anthropic.com/v1`; switching back restores the OpenAI default. Explicit custom proxy URLs are preserved. Model discovery uses the provider's `/models` endpoint with the correct authentication and bounded Anthropic pagination. Catalogs are cached briefly per connection; provider failures are shown without hiding other connections' models. Returned names, token limits and image capabilities are used when supplied. For APIs without discovery or for custom capabilities, add manual model overrides under **Advanced settings** in provider settings. Missing capability information uses conservative defaults; review overrides for your endpoint as needed.

Keys are encrypted in SQLite using the persistent auth secret and never returned to the browser or workers. Blank key updates preserve the saved key. **Clear key** marks it for removal when you save; **Undo** restores it before saving. Entering a replacement key cancels pending removal. Changing an endpoint URL or API format requires re-entering or clearing its saved key. Local HTTP endpoints are supported; use HTTPS for remote providers. Requests reject redirects. In Compose, `127.0.0.1` refers to the API container: use `http://host.docker.internal:8000/v1` for a host model server, or a reachable service address. The host server must listen on an interface reachable from Docker. Provider settings apply to all accounts. Token usage is recorded locally; currency costs are not estimated for custom providers.

## Runs and GitHub

Run transcripts always label messages with the Gond Agent mark and **Agent**, whichever model runs, including retired runs. Model and provider information stays in model pickers, run details, Settings and usage. Transcripts keep agent messages readable and group routine activity into expandable summaries. Open a summary for file names, commands, diffs and output. Failed actions stay visible, and API and ChatGPT plan runs use the same plain activity labels. Runs created by the removed Claude Code and Codex agents keep their transcripts and diffs but can't take follow-ups; start a new run to continue that work.

Linked pull requests refresh while viewing the workspace, including after merging or closing them on GitHub. Merged PRs show a purple merge icon in the run list, header and PR panel. Reads share a short cache; if GitHub is unavailable, the last known state stays visible. Active work can finish before its merged run is closed.

Run change counts and saved diffs use the merge-base with the current base branch, not the task's original commit, so merging newer main changes does not count them as the run's work. Publication refreshes the base in the service checkout using the owner's GitHub connection, with bounded shallow-history deepening. Offline comparisons use the last known base head; if ancestry is unavailable, the last diff is kept without failing publication. Linked PR totals take precedence when GitHub reports them for the published commit, are cached per account, and refresh on publication and workspace reads. Older runs update lazily. Compact list counts abbreviate large values and expose exact counts in their tooltip; run details retain exact counts.

The worker uses a plain workspace prompt; callers supply their own process and verification requirements. `repo_map` gives a requested, ranked repository overview before broad searches; it is not automatically injected. `symbols` provides parser-backed file outlines and exact definitions through Universal Ctags, plus explicitly lexical references. `batch` returns ordered results/errors for up to eight independent reads, searches, symbol queries or background-output reads; it cannot execute commands or write files. Persistent agent memory has been removed; repository `AGENTS.md`, `GOND_AGENT.md` and `CLAUDE.md` instructions still apply.

The worker image includes pinned Playwright, Chromium, fonts and browser dependencies. The `browser` tool runs a supplied Playwright test body with `page` and `expect` independently at 1440×900 and 390×844, returning screenshots to the model and transcript alongside console/network failures. Start app servers with background `bash`; custom browser tests can import `@playwright/test` through the worker's `NODE_PATH`. Use an image-capable model to inspect screenshots. Browser execution stays inside the worker container, with no host credentials or host browser access.

For step-by-step checks, `browser_open(url)` starts a persistent page; `browser_snapshot()` returns bounded page text and interactive refs such as `e1`. Use `browser_click(ref)`, `browser_fill(ref, text)`, `browser_press(key)` and `browser_wait(text | ms)` to interact, then `browser_screenshot(viewport: 1440 | 390, ref?)` to inspect the result. `browser_logs(kind: console | network, since?, limit?)` returns error-first cursor pages; `browser_close()` deletes the session. Navigation invalidates refs. One page is shared within a working turn; child tool contexts share it internally, but current subagent policies grant no browser tools. Close, Stop, turn completion or ten minutes idle removes its browser and private profile. Screenshots are normalized to at most 1568 pixels per side and 1 MiB. Page text, logs and images are untrusted content, not instructions. Text responses use matching random per-response delimiter IDs, with the complete frame capped at 30,000 bytes.

The persistent browser uses a DNS-pinning filtering proxy: public HTTP(S) and container-loopback app servers are allowed, but metadata, LAN/Docker-gateway destinations and reserved ports 8787/8788 are blocked, including redirects. Child `about:blank` and `about:srcdoc` documents work normally; non-HTTP(S) main-frame navigation closes the session. Other non-HTTP child documents are removed after commit, and subframe network traffic still passes through the same filters. Downloads, popups, WebRTC and permission grants are disabled. Chromium runs without its own sandbox; Docker remains the containment boundary. This policy does not restrict the unchanged arbitrary-script `browser` or shell commands. See [browser implementation and checks](containers/browser/README.md).

CI verifies both real-browser suites and both compiled-worker smokes against the finished worker image under its 2 GiB memory limit and non-root, read-only runtime restrictions. Only Chromium-free unit tests run during image builds; the mandatory smoke gate retains all security checks and blocks publication on failure.


The service uses the run owner's effective GitHub connection for repository API calls and HTTPS Git operations. It shallow-clones only the requested branch (`--depth 1 --single-branch --no-tags`), rather than downloading the entire repository history. Full history and other branches are not available inside workers. The run shows download/checkout progress, repository packing, container startup and agent startup separately. Compressed checkout archives are limited to 128 MiB so their base64 controller messages fit safely; an oversized checkout fails with a plain explanation instead of attempting an invalid transfer.

The repository archive enters the run's private workspace volume over Docker's attached stdio. A loopback model relay multiplexes model requests/responses over the same channel, scoped to that run; no model/control ports are published. At turn end, the worker returns a git bundle; the service imports only its objects with hooks disabled and pushes the named run branch. Existing upstream history is preserved. Restarted runs shallow-clone their saved run branch and fetch the original base revision for recovery and evidence checks.

The control service generates a fresh random relay credential for each worker start and passes it in the runner's environment, not its command line. Every relay request requires bearer authentication; requests with an Origin header or an unexpected Host are rejected, and POSTs must use JSON. The API never receives or stores this credential. Shell, checks, browser and MCP subprocesses do not inherit it. This prevents hostile web pages visited by the browser tool from spending the owner's model or search quota; it does not protect against code the agent runs itself. Same-UID code can read the runner's environment through `/proc`. The container remains the boundary, and Docker stdio control trust is unchanged.

For healthy workspaces, Stop only interrupts the current turn; it retains the workspace and uncommitted edits for a follow-up, keeping the slot until closed or safely released for waiting work. For work waiting for capacity, Stop cancels the queued work instead. Stopping a kept failed workspace releases it immediately (see below). Follow-ups continue in the same container while it is alive. Active workspaces have no elapsed-time, idle, step or tool-call budget. Successful idle containers normally persist, but safe idle workspaces may close automatically when work is waiting and all slots are occupied (see below). Explicit close, merge, delete, service shutdown/recovery also release them; monitor capacity and disk use. The retired `RUN_IDLE_MINUTES` and `RUN_TURN_MINUTES` settings are ignored. A service restart marks working runs with a usable checkpoint **interrupted**, preserving the checkpoint for automatic or manual recovery; without one, it marks them failed and follow-ups use the last pushed branch. Work after the last completed checkpoint can be lost. Recovery removes orphaned Docker resources labeled with this instance's persisted identity, without touching other instances; capacity-queued work survives with its queue sequence and pending work. Run history and diffs persist locally. Merging destroys the workspace. Deleting a run hides it immediately; stored history is purged after 30 days.

Automations supports daily/weekly local-time schedules and the automatic pull-request preference. Occurrence claims prevent duplicate scheduled runs. General GitHub issue/check/PR polling and issue-triggered runs remain removed. The scheduler never polls GitHub. Existing run history is preserved and obsolete polling preferences are removed on upgrade. Manual pull-request creation/merge remain available; linked PR state otherwise refreshes only on authenticated workspace reads. Model requests go directly to the configured provider. Local usage records have no account limits or feature gates.

### Evidence transparency

The ledger is **evidence recorded by the worker**, not independent proof or review. A separate-container rerun is the only way to supply independent proof and is out of scope here. Signatures authenticate records to the API; they do not establish correctness. Tests can print fake summaries/counts or call `process.exit(0)` before assertions run: counts and exit status are worker-reported observations, so this is transparency, not enforcement. Same-UID code executed by the agent can inspect runner process memory, so the container remains the trust boundary.

The advisory gate is enabled by default. For changed work it asks for:

- One fresh successful check: an eligible `run_checks` command/cwd pair, exit 0, environment allow-list applied, and a **positive parsed test count**. Both pre/post tree hashes must match the final publication tree, and `command_definition_changed` must be false. Command definitions/configuration are compared against pinned BASE before and after execution; changed definitions cannot satisfy the gate or count as publication success and produce weakening warnings. Node, Cargo, pytest and Vitest/Jest-style summaries are recognized; unknown counts and zero tests do not pass, even at exit 0. An eligible lint/typecheck command alone usually cannot satisfy the test-count requirement.
- A fresh UI **attempt** when changes touch `web/` or any `.tsx`/`.css` file. `browser` and `browser_open` record attempts, even when unsuccessful; URL/title are metadata only, not proof of visual correctness, assertions or review. Titles are parsed from actual browser output when available, otherwise empty; URL credentials, query and fragment are removed.

The check waiver is fixed: only regular `.md` files at repository root or anywhere under `docs/` qualify as docs-only. Markdown elsewhere (including `protocol/README.md` and `runner/CHECKPOINTS.md`) is not waived. There is no configurable docs/test-glob override. A no-change follow-up consumes no gate rounds.

Only foreground `run_checks` with an **exact** eligible command and `cwd` records checks. For example, use `{"command":"npm test","cwd":"api"}` when that pair was discovered, not `cd api && npm test`. `cwd` defaults to `.` and must stay within the repository. `bash`, background checks and command variants do not produce check records. Summary parsing is bounded and may be inconclusive; no record or unknown count is not a pass.

The clean-check allow-list preserves non-secret image toolchain locations, including `PLAYWRIGHT_BROWSERS_PATH`, `NODE_PATH`, `BUN_INSTALL` and `BUN_INSTALL_CACHE_DIR`. Only exact eligible foreground checks receive the clean environment snapshot; other `run_checks` calls (including background calls) inherit browser/toolchain variables while omitting `GH_TOKEN`, `GITHUB_TOKEN` and every `GOND_AGENT_*` variable, including the relay token. `env_clean` records that an environment allow-list was applied; `env_digest` is a SHA-256 digest of the actual snapshot's values. This is not a secrets scan or proof that no secrets were available: HOME, `.npmrc`, repository code and same-UID processes may still expose credentials/configuration. Tree identity includes HEAD-tracked files and non-ignored worktree files, using isolated Git configuration without clone-local/system excludes. It still respects worktree `.gitignore`: ignored paths are NOT covered, even if executed during a check. Do not treat hidden ignored code as trusted. Ignored dependencies such as `node_modules` may be lost on restore.

The gate only continues clean main-agent `end_turn` responses, not subagent, interrupted, error or compacted stops. It allows at most **two rounds per turn, six per run**, and no further rounds at **ten resumes**; actual runner counters survive sealed checkpoint state. Separately, RunService durably reserves up to two rounds in `gate_budget` at `next`, before each task is delivered, capped at six. Worker startup is seeded from `max(gate_rounds, gate_budget)`, so a crash may spend unused allowance but cannot replenish it. `declare_unverified {reason}` is the explicit advisory escape. Declarations and budget-exhaustion limitations always appear under **Not verified** rather than failing the run or preventing publication.

#### Repository and deployment policy

Policy and manifest commands are discovered once from the run's pinned original base, not from the agent's edited working tree, and remain frozen for that worker/turn. Defaults discover `npm test`, `npm run lint`, `npm run typecheck` where the corresponding scripts exist, `cargo test --locked`, `cargo clippy --all-targets --locked -- -D warnings`, and `pytest` from recognized pytest manifests.

A regular base-revision `.gond-agent/evidence.toml` can add checks:

```toml
# All fields are optional. Defaults: enabled = true, ui = "attempt".
enabled = true
ui = "attempt"
checks = [{ command = "npm test", cwd = "api" }]
```

The file is strict TOML, at most **16 KiB**. Only `enabled` (boolean), `ui` (`attempt`/`none`) and `checks` (up to 32 `{command,cwd}` entries) are accepted; unknown fields, including nested ones, reject the policy and retain defaults. Checks are **additive**, never replacements. Commands use a fixed allow-list grammar, at most **200 bytes** with single ASCII spaces: `npm test`; `npm`/`pnpm`/`bun run <script>` with a nonempty script in pinned BASE's `package.json` at the exact cwd; locked Cargo test/fixed clippy; and fixed pytest/`python3 -m unittest` forms. Arbitrary executables, URLs, quoting, expansion, shell operators, redirection, globs and wrappers are rejected. See [the protocol](protocol/README.md#frozen-policy-and-gate-behavior) for allowed flags. `cwd` is `.` or a normalized repository-relative directory, without `..`. Adding a command only makes it eligible; it does not establish that it ran meaningful tests.

Set **`GOND_AGENT_EVIDENCE=off`** in the API service environment to disable the advisory gate. **`GOND_AGENT_EVIDENCE_REPO_POLICY=allow-weaken`** permits base repository `enabled=false` or `ui="none"`; without it, weakening is refused and noted. These are deployment controls, not tool arguments; `allow-weaken` never bypasses command grammar or BASE-script validation. Default Compose forwards both settings from `.env`, with `GOND_AGENT_EVIDENCE` defaulting to `on`; `.env.example` includes that default and documents the optional repository-policy opt-in. Policy edits cannot alter frozen checks; they apply only on a later run whose pinned base includes the edit and are flagged as evidence weakening.

#### Publication output

Every published description uses the single `descriptionFor` policy: explicit PR prose, otherwise eligible final reply, otherwise title, followed by a **service-generated Verification block**. This also applies with the gate off, docs-only work, no evidence, manual PR actions, and workspace/MCP descriptions. Caller/model Verification headings and markers are neutralized so they cannot impersonate the generated block. No repository PR-prose file is needed or created for this policy; live transcripts remain unchanged.

The API service generates a fresh random **32-byte key per worker**, sends private `init_evidence {request_id,run_id,owner_id,key}` **before the first task**, and waits for `state.evidence_initialized {request_id}`. It retains the key in live memory and sealed checkpoint state, never environments, ordinary run rows, transcripts or logs. No worker-generated or exported key is adopted as signing authority. HMAC-SHA256 signs recursively key-sorted compact JSON `{domain:"gond-agent:evidence:v1",run_id,record}` with all record fields except `sig`, including run_id, sequence, both tree hashes and `command_definition_changed`. Incoming records undergo strict schema/signature validation and replay/duplicate/out-of-order rejection. Before each push/retry, including retained or reclaimed commits, the service derives freshness from the **exact pinned commit's tree**, not from model prose or a worker's freshness claim. It classifies actual base-to-head diff paths into `ui_required` (`web/` or `.tsx`/`.css`) and `docs_only` (only regular root/`docs/` Markdown files).

The generated block reports fresh successful checks, failures/inconclusive results, stale/zero/unknown counts, frozen policy and gate counters, **Not verified** limitations and **Evidence weakened** warnings. Diff heuristics flag removed/changed tests, new skips/narrowing, script/test/CI configuration changes and policy edits; absence of a warning is not proof of coverage. Missing-UI warnings follow the actual diff-path classification and UI policy. Details show command/cwd, exit, duration/start time, test count, environment flag/digest, UI metadata and bounded scrubbed output. The API retains up to 40 public records with the active red/green pair pinned, and the block summarizes every retained record with command/cwd, exit, freshness, test count and duration. At most eight records are detailed, preferring failures and UI attempts, with a 1,200-character output excerpt each and a roughly 23,000-character block detail budget; omissions/truncation are disclosed. See [the event and publication contract](protocol/README.md#execution-evidence-and-publication) for exact schemas and retention limits.

### Failing regression first

Runs and MCP `start_session` may explicitly supply `kind` (`bug`, `feature`,
`refactor`, `other`); omission is never inferred from prose. Callers should set
`kind:"bug"` for known bug tasks: a model declaring `feature` skips bug rules.
For bug fixes, call
`declare_task` first, add a regression test, run `run_checks` with
`{repro:"red",test_files:["regression.test.ts"]}` before production edits, then
run the same tests with `repro:"green"` after the fix. Red requires a real
assertion failure while the isolated non-test tree still equals pinned BASE;
compile/import/syntax failures do not qualify. Green pins the same test contents
and test ids, and requires a non-test change since red; flaky no-change passes
and test-only edits do not qualify. Red only records that some assertion in a
new or changed test failed on base code. An unrelated or trivial assertion can
still qualify if it later passes after a non-test change; this does not establish
relevance or causality. Ordinary checks remain separately required.

Supported repro reporters are Vitest/Jest JSON, pytest JUnit, Cargo's stable
assertion harness and Go JSON. The execution limit is 120 seconds. Unsupported
runners or non-local repros use parent-only `skip_repro` with
`no_cheap_test_path`, `needs_external_service`, `ui_only` or
`cannot_reproduce_locally`. A skip is disclosed, not a pass. Subagents cannot
change task classification or skip state.

The service makes a tests-only local commit after admitted red, then the normal
fix commit. Staging moves worker HEAD and the index mid-turn, preserving the
worktree but changing `git status`. A busy lock or concurrent commit may prevent
staging. Recovery/busy boundaries may defer exact red-tree reconstruction to
publication; unavailable staging is disclosed as `single commit`. The signed
sequence survives sealed checkpoints and is pinned against ordinary record
retention. Generated Verification includes kind, red/green commands, matching test
id and bounded fenced tails, or skip reason. This is transparency recorded by the
worker, not independent proof. See [the regression contract](protocol/README.md#failing-regression-first)
for supported paths, reporter limitations, staging and checkpoint behavior.

### Checkpoints and interrupted-run recovery

Automatic CI fixing has been removed. Finished workspaces stay available until explicit close or safe idle release for waiting work. Legacy `ci_*` members in stored run JSON (including `ci_active`, `ci_turn`, `ci_publication_pending` and `ci_round`) are unused and ignored by `parseRun`; old checkpoint service metadata is also ignored. No database columns are dropped and no migration rewrites stored JSON.

The runner offers paired work-tree/conversation checkpoints at turn start and completed main-agent rounds, holding agent dispatch until persistence finishes. Ordinary capture attempts are at least 30 seconds apart; intervening boundaries release immediately. Unchanged tree/history/pins skip bundle creation and persistence. There is one capture in flight plus at most one pending boundary. Before publication the service waits for checkpoint work; after pushing it forces another capture. Save/flush/capture failures emit `run.checkpoint_unavailable` and never block publication: a failed save leaves the previously saved pair available, but recovery never searches behind an invalid latest pair and may fall back to the last pushed branch or fail after restart. Background shells, dev servers and watchers can keep writing while dispatch is held; tracked live background shells reject capture, but untracked processes are not frozen. This is not filesystem-level quiescence. No unfinished work is pushed to GitHub for a checkpoint, and Docker volumes are not retained as a recovery mechanism.

Checkpoint failures include an additive fixed-vocabulary `reason` in `run.checkpoint_unavailable` events (available through run/event reads), while keeping the ordinary message plain. `tree_too_large` means the **compressed changed-tree bundle** exceeds 64 MiB; `state_too_large` means the **full stored JSON conversation/state** exceeds 4 MiB, including the API wrapper. State includes all stored images, not only the newest eight sent with model requests: three near-1-MiB images become roughly 4 MiB of base64 before JSON/history overhead. Long command output histories can also reach this limit. Non-ignored untracked build output or screenshots **inside the checkout** join the tree; worktree `.gitignore` exclusions remain respected, and files outside the checkout (such as `/tmp` screenshots) are not bundled. Newly staged ignored files fail separately with `staged_ignored_files` rather than being silently lost.

Other reasons are `storage_limit` (the pair exceeds the configured storage budget), `storage_failed` (fixed filesystem error codes), `timeout`, `background_shells_active`, `busy`, `worker_unavailable`, `invalid_state`, `git_failed` and `unknown`. Older workers or unclassified failures report `unknown`; raw runner errors, paths, history and exception text never enter this field. The controller preserves safe runner state errors and emits a separate allow-listed reason through private transport. Timeouts can arise at the 120-second state-control deadline, an individual 120-second Git command, the 180-second API transport deadline, or the shorter 10-second final-release capture deadline. A final capture retries the same machinery: it cannot bypass a persistent state/tree cap or a live background-shell rejection. **No limits were raised.** Historical generic events cannot establish which cause occurred; the number of changed files alone is not a byte-size measurement.

Finishing is coordinated by RunService: it saves a finishing-phase marker before awaiting checkpoint flush, then exports private evidence before publication. An unavailable export or malformed evidence does not reset durable budgets, replace the service's signing authority or prevent publication and post-push capture. A failed flush does not suppress that later capture attempt. Run state is reloaded after awaits so a follow-up or Stop accepted while finish is settling is preserved; finishing-phase recovery verifies publication rather than repeating the completed task.

Service waits for evidence initialization and private evidence export are limited to 10 seconds each. The evidence path's checkpoint flush waits up to 30 seconds, with a further bounded 30-second drain after timeout before abandoning advisory evidence work. Explicit Close and automatic idle release settle execution evidence before publication/teardown, including stopped sessions; automatic release preserves existing paired checkpoints and does not publish stopped work. Failed turns and exited workers record unavailable policy status without an evidence RPC; exited workers release capacity without waiting for evidence. After worker destruction, unrelated queued runs can start while checkout cleanup finishes; reopening that same run waits for its cleanup. These evidence wait limits do not cancel underlying checkpoint work or bypass held-checkpoint snapshot safeguards.

On restart, working runs with a usable checkpoint become **interrupted**. With `GOND_AGENT_AUTO_RESUME` unset or anything other than `0`, eligible `web`/`mcp` runs resume through the persistent workspace queue: at most two automatic resumes per run, only from checkpoints no older than 24 hours, one automatic recovery at a time. Scheduled/unknown-source runs do not auto-resume. Quota-limited or inaccessible runs are skipped and kept for a person. Use **Resume**, send a human follow-up (MCP: `send_session_message`), or call authenticated `POST /api/v1/runs/:id/resume` to continue manually. MCP has no explicit resume tool: `send_session_message` resumes through the queue, and `get_session`/event reads report `state:"interrupted", done:true` (not successful completion). Never-started queued runs keep their pending work and queue order.

Resume claims are transactional and owner-scoped, released on worker loss/closure, and expire after a ten-minute lease so stale claims cannot pin retention/quota indefinitely. Unusable checkpoints are quarantined after validation/restore failure rather than retried. The new worker uses the run owner's current GitHub/model access. Invalid or unrestorable checkpoints fall back to a fresh checkout of the last pushed branch with a visible `run.checkpoint_fallback` event. Successful restoration emits `run.resumed`; the continuation warns that external effects may already have happened and must be checked before repeating them.

A checkpoint pairs a private tree bundle with the runner's **stored** conversation (including compaction notes and all stored images), plan, counters and evidence ledger. State schema version is 1; service and runner both use compatibility epoch `gond-agent-checkpoint-4`. **Epoch 1 is rejected**: its unrestricted subagent ID counter is incompatible with epoch 2's consumed bounded-delegation allowance. **Service recovery also accepts the latest authenticated ledgerless epoch-2 sealed checkpoint**, with `evidence` absent or null. It authenticates under the original epoch-2 storage key and requires the payload version to match the authenticated row/envelope. Epoch-2 ledgers and future epochs are rejected too; ciphertext/rows are never relabeled, and recovery never searches older checkpoints when the latest pair is unavailable or incompatible. Claim, release, quarantine and consumption retain the original epoch-2 key. The runner codec upgrades accepted state in memory to epoch 4 without inventing prior execution evidence; the next normal paired capture seals a new epoch-4 checkpoint and transactionally consumes the claimed predecessor. Resume rekeys for the new worker, leaves old records historical/stale without re-signing them, and preserves sequence and budget counters. The ledger retains up to 40 strict typed records, policy, signing key, staleness/limitations and gate/resume counters. The worker creates the tree commit with a temporary index without moving HEAD, the branch or the real index. Restore verifies the single allowed bundle ref, object integrity and pinned base/HEAD in a throwaway repository **inside the new worker**, then applies only the tree. The API stores bundle bytes without invoking Git on them.

Staging metadata is not restored. Export rejects newly staged files that match ignore rules rather than silently losing them during capture or later publication; ordinary ignored, untracked files are excluded. Publication snapshots and checkpoints use the same isolated Git helper as evidence tree capture: they ignore clone-local/system configuration and excludes but respect worktree `.gitignore`; ignored code is NOT covered by a matching tree hash, even if a check executes it. Ignored dependencies such as `node_modules` may be absent after restore. A state RPC has a bounded write/reply deadline; a failed or partial pipe write discards the worker because its JSONL stream is no longer safe to reuse.

Storage lives under the API data directory's `checkpoints/<run_id>/`: directories are mode 0700, files mode 0600, publication is temporary-file + rename before transactional metadata insertion. Conversation state and base/HEAD/checkpoint revision pins are sealed with the persistent auth secret and bound to the owner, run, version, creation time and bundle digest. **The Git bundle is not encrypted: the API data volume is its trust boundary.** Treat that volume and its backups as private source code. Checkpoints do not collect raw environment values; evidence state includes an environment allow-list digest and a private signing key. Source files and tool output can themselves contain secrets; this is not a content-redaction system.

Storage defaults to 1 GiB total (`GOND_AGENT_CHECKPOINT_MAX_MB=1024`) and seven-day retention (`GOND_AGENT_CHECKPOINT_RETENTION_DAYS=7`), both positive integers. It caps each bundle at 64 MiB and stored state at 4 MiB **including the service wrapper**, keeps the latest two snapshots per run, and evicts consumed/ordinary checkpoints before unconsumed interrupted ones. Cleanup deletes real files and sweeps crash orphans at startup and hourly on an unref'd timer; shutdown clears that timer. Explicit close, Stop, merge, run/account deletion and retention remove checkpoints in application code; shutdown and safe idle release preserve them. Compose forwards `GOND_AGENT_AUTO_RESUME`; storage-limit overrides require an explicit Compose environment override.

Runner import rejects incompatible versions, wrong run/owner, system roles, unknown schema fields, unpaired tool calls/results and oversized state. Imported images pass through the existing raster normalizer. RunService uses private initialization for the service-issued evidence key and private export for policy/counter metadata. State replies use a separate controller RPC path, never the ordinary event/transcript stream. See [the internal protocol](protocol/README.md#checkpoint-controls-and-recovery) and [runner contract](runner/CHECKPOINTS.md).

Only model-authored pending questions are quoted as data; recorded human answers are delivered as ordinary user text. Old live question/request IDs are **not** restored. The model may ask again with a new ID. Resume framing is added at delivery without mutating stored messages, and repeated restores rebuild synthetic continuations rather than stacking prefixes. Recovery from the finishing phase asks to verify publication and finish, never to replay the original task. External effects, shells/processes, tool runtime state (including browser sessions/profiles/refs and LSP processes), installed tools/the tools volume and live subagents are never restored. Reopen the browser and take fresh snapshot refs; LSP restarts lazily. A checkpoint is not exactly-once execution: effects after its boundary may have happened even when they are absent from restored history.

### Waiting for a workspace

`MAX_ACTIVE_RUNS` limits distinct live plus booting workspaces, not just working turns. Ready, idle, stopped and model-failed workspaces still occupy slots while live. Browser/HTTP creates, MCP starts and follow-ups that reopen a closed workspace are validated first, then queued when capacity is unavailable. Accepted work starts automatically: the service drains on release, admission and startup, with a 60-second safety net. You do not need to retry or poll to start it.

Waiting work is FIFO within each account; the account with the fewest occupied workspaces is served first. `queue_position` is 1-based and `queue_length` counts only your account's queued runs. These show relative FIFO order within your account, not a global position or guaranteed start rank. HTTP starts/get/list/event reads and MCP `start_session`, `get_session`, `list_sessions` and `read_session_events` include these additive fields while waiting, plus `capacity: {max, occupied, working, idle_releasable, queued_total_for_account}` and `queue_reason`. Capacity counts are instance-wide except `queued_total_for_account`, which only counts your waiting runs. This deliberately exposes coarse shared-instance load so contention is understandable even when your own account is idle. Counts may reveal other accounts’ activity, but never their identities, repositories, run details or queue lengths; this is operational visibility on a shared self-hosted instance, not strict tenant activity isolation. Each queue-change pass computes the shared load once, then attaches account-local queue totals. `working` includes startup; `idle_releasable` counts workspaces currently eligible for safe automatic release, not every idle workspace. The reason explains, for example: "All 5 workspaces are in use: 2 working, 3 idle. Idle workspaces can be closed to free a slot." No ETA is promised. Queued rows show this reason and point to **Close workspace** on idle runs when safe idle capacity exists. Live events include `run.queued {position,length,capacity,queue_reason}` updates and `run.dequeued`.

Set positive integers in `.env`: `GOND_AGENT_QUEUE_MAX=50` limits total waiting runs, `GOND_AGENT_QUEUE_MAX_PER_ACCOUNT=10` limits waiting runs per account, and `GOND_AGENT_QUEUE_WAIT_HOURS=24` sets maximum waiting time. Compose forwards all three. Full queues return HTTP 429 `queue_full`: "Too many runs are waiting. Try again later." Waiting longer than the configured limit fails with a plain message; this expiry applies only to the queue, never to an active workspace.

With waiting work and full capacity, the service automatically closes one safe idle workspace per drain pass, oldest idle first, using the shared close path. Ready sessions snapshot/push first; verified clean stopped sessions close without publishing. `GOND_AGENT_IDLE_RELEASE_SECONDS=600` sets the minimum idle age; `0` disables automatic release. Compose forwards it. A workspace must be ready or stopped, have no pending messages, open question, pending publication or resume, and have a clean worker worktree whose HEAD equals the confirmed pushed head. A stopped workspace that never pushed anything is also eligible when its clean HEAD still equals the pinned original base; clean but unpublished commits are not safe. Working, interrupted, resuming, failed-with-kept-work and merged-pending workspaces are excluded from this safe-idle policy; failed-kept pressure reclaim is separate below. An unconsumed checkpoint claim also blocks automatic release. Automatic release of stopped work never pushes or creates a branch; uncommitted or unpushed work prevents release. Automatic idle release uses `close(id, false, true)`, preserves paired checkpoints and marks the run for checkpoint restore; explicit Close still discards them. A safely published ready workspace can release whether its linked PR is open or merged; PR state alone does not block release. Fresh worker evidence is checked before closing; missing evidence fails closed. Workspaces with stashes, unpublished commits on other local branches, local tags/notes, submodules or remaining tool/background processes are conservatively excluded, since their work may not be preserved by a parent snapshot. Files hidden only by `.git/info/exclude` also block release: the evidence probe explicitly ignores clone-local exclusions independently of checkpoint capture. Ordinary `.gitignore`-ignored untracked files remain excluded like publication. Dirty/unavailable evidence is retried on later drain ticks. History/diffs remain readable; follow-ups on unmerged runs restore the saved conversation and tree in a fresh worker when a usable checkpoint exists, otherwise fall back to the pushed branch with a plain notice. A new follow-up does not replay the completed task. Merged runs still require a new run. The transcript explains `run.released {reason:"idle_for_waiting_work"}`. Releasing a slot never bypasses account-fair queue admission. Idle release is demand-driven, not an active-turn timeout; the 60-second drain safety net means the minimum age is not an exact release deadline.

Failed workspace destruction retains its occupied slot and retries automatically up to five total attempts, with 1s/2s/4s/8s backoff. Exhaustion emits `run.cleanup {state:"gave_up",attempts:5}` and a plain transcript message. Try **Close workspace** again or ask an administrator to check the worker service; a failed destroy never admits another worker into an occupied slot. Shutdown cancels automatic retries; normal instance-scoped restart cleanup still applies.

Stop cancels waiting work. Once a run has started, **Stop keeps its workspace and occupied slot until it is explicitly closed or safely released for waiting work**. The idle delay starts when the worker actually stops, not when Stop is requested. Closing or removing waiting work also cancels it. Close a retained live workspace to free a slot and automatically start waiting work. Scheduled runs (`source: runner`, also `schedule` supported) never enter or jump the queue and are not subject to its bounds. They fail fast with `run_limit` when capacity is unavailable or the queue is nonempty. Later scheduler ticks may retry, but scheduled runs can be refused for a long time while the queue remains nonempty.

Per-run message request-ID receipt rows grow by one small row per accepted message and remain for the life of the run, even after the message is processed. They prevent duplicate messages on retries and are deleted with the run.

### Commit identity

The service resolves the run owner's effective GitHub connection and caches its login and numeric ID per token. Checkout configuration and every snapshot use that identity for both author and committer: `login <id+login@users.noreply.github.com>`. Missing connection identity fails clearly; global Git identity is not a fallback. Optional `GOND_AGENT_COMMIT_NAME` and `GOND_AGENT_COMMIT_EMAIL` override individual fields (including in Compose). Pull requests use the connected account. Publication adds no attribution, trailers, or product signature; commit/PR titles use the optional title or task, and PR bodies follow the precedence above. Caller/model prose is subject to the shared Verification neutralization and generated evidence block; the live transcript is not rewritten.

### Driving Gond Agent from another bot

Use the authenticated remote MCP tools to discover models, start idempotent sessions, wait for completion, inspect diffs, send follow-ups and open PRs. See [the full contract and JSON examples](protocol/README.md#driving-gond-agent-from-another-bot). Completion ends the current turn, not the session: a follow-up starts more work. Tool selection follows the task and repository instructions; changed work can trigger the bounded advisory evidence transparency gate described below.

Finished runs retain capacity until closed manually or released safely for waiting work: use MCP `close_session` or More → Close workspace to save/push changes and release the slot without deleting history, automatically starting waiting work. Busy live workspaces cannot close; closing capacity-queued work cancels it. Snapshot/push failure preserves the workspace. Follow-ups reopen the pushed branch, queuing if needed. `MODEL_STALL_MINUTES` defaults to 10 (0 disables): requests abort only when headers or stream bytes stop arriving, never because a progressing response takes a long time. Missing GitHub identity intentionally fails checkout with a 409 because publication requires the connection. Identity caches expire after one hour and are invalidated on GitHub command failures (including unauthorized responses).

### Transient failures and kept work

GitHub GET requests and network Git clone/fetch/push retry transient network, certificate/TLS, timeout, HTTP 5xx and 429 failures up to five total attempts. GitHub writes (including PR creation, editing and merging) retry only proven pre-send DNS/connection-refused/TLS-handshake or certificate failures, or HTTP 429/503 with an explicit valid Retry-After wait; timeouts and dropped responses are ambiguous and are never replayed. Backoff starts at one second, doubles with full jitter and is capped at 30 seconds; Retry-After can require a longer wait. Foreground GitHub calls share a 60-second total deadline across attempts and waits; only background publication opts into the full schedule. Authentication failures, other HTTP 4xx, rejected/non-fast-forward pushes and unknown errors stop without retrying. Transient model failures retry the same request up to five total attempts, before executing the response. Exponential full jitter uses a 2-second base and 60-second cap; Retry-After is a minimum capped at 120 seconds. The transcript shows each wait and attempt; Stop interrupts it immediately. Authentication, billing/quota, invalid requests, context overflow and plan usage limits do not enter transient retries; usage-limit reset times are shown when supplied. Exhaustion names the safe failure class and actual attempt count rather than replacing every cause with a generic connection error. Failed turns keep existing work without opening or updating a PR. The shared policy and old/new classification tables are described in [model retries](docs/model-retries.md). A stream-reset event removes a retried attempt's partial text from the transcript and service summary, so the final reply appears once. This also works when a turn compacts context between tool rounds: compaction markers remain visible and summary retries cannot duplicate main-agent text. Main-agent compaction clears the publication reply candidate, so a recovered reply never includes incomplete pre-compaction text; the earlier transcript remains visible. Transient backoff runs at one layer only; context overflow goes directly to the compaction path, not an unchanged-request retry. Summary retries count toward the existing 16-request compaction cap.

Explicit new branches use a create-only lease until their first publication is confirmed: every attempt keeps the same pinned commit and `--force-with-lease=refs/heads/<branch>:` with an empty expectation; later pushes are ordinary non-force pushes. The existing exported `publicationPushOptions(run, beforePush?)` helper in `api/src/runs/publication.ts` composes the lease and optional per-attempt policy hook for the initial import, retained-publication retries and republishing capacity-reclaimed `kept_commit` commits. It sets `lease: "create-only"` only when `run.explicit_branch && !run.pushed` and forwards `beforePush` as `PushOptions.beforePush({cwd,branch,head})`. Explicit branches are supported by workspace/API and MCP requests, and explicitness is persisted rather than inferred from a branch name. `importBundle` keeps retry options as its fifth argument and push options as its sixth.

A stale-info rejection counts as success only if an owner-authenticated remote-ref read equals the exact commit sent, allowing a lost successful response to be reconciled without weakening the lease. A branch created by someone else between attempts is never overwritten, even if a plain push could fast-forward it. A different, missing or unreadable ref remains rejected, with no plain-push fallback. The helper's generic `beforePush` argument runs before every push attempt through the retry scheduler's `beforeAttempt` hook, outside retry classification. A policy refusal propagates unchanged and prevents the push; it is never retried as a transient failure.

If a turn or publication still fails, its message names the failing step and attempt count. Without queue pressure, the workspace and service-side clone remain available for up to **60 minutes**, count toward `MAX_ACTIVE_RUNS`, and expose `work_kept:true`. Send a follow-up during that window: the previous turn's kept snapshot/commit is pushed before new work starts, without re-cloning or losing unpushed changes. Set `GOND_AGENT_FAILED_KEEP_MINUTES` in `.env` to change the grace period; `0` releases immediately. It accepts nonnegative whole minutes within the platform timer range.

At full capacity with waiting work, queue pressure reclaims the oldest nonbusy kept failure after a short **60-second retry grace**, independently of the safe-idle-release setting. Before releasing a live failed workspace (expiry, immediate release with a zero grace period, capacity reclaim or shutdown), the service attempts one final local work-tree/conversation checkpoint, bounded to **10 seconds**. The attempt is recorded before capture starts; destruction retries do not capture again or add another capture deadline. This does not snapshot for publication, push, or create/update a PR. A successful save changes the failure message to **“Your changes and the conversation are saved; send a follow-up to continue.”** After release, the follow-up restores that pair through the existing verified-restore path. A follow-up during final capture receives `workspace_closing`; retry after release. In-window follow-ups still use the original live workspace, without an extra capture. Replacement startup waits for completed destruction. Already-imported commits and API clones also retain their existing `kept_commit` retry behavior; unpublished branches stay unpublished until their exact commit is confirmed pushed. Snapshot/import failures drop large in-memory publication bundles and re-snapshot the still-kept worker on follow-up.

If final capture fails, times out or exceeds the existing size/storage caps, any older valid checkpoint is discarded too (unchanged behavior). The failure message says the changes and conversation could not be saved, and follow-ups fall back to the last pushed branch (or an already saved imported commit). Late capture replies cannot recreate a closed workspace's checkpoint. Checkpoint retention, caps and eviction are unchanged: a saved pair is not an indefinite backup. An already dead worker keeps the existing last-checkpoint recovery behavior; it cannot produce a new final capture.

**Stopping or explicitly closing a still-kept failed workspace releases it and discards its recovery checkpoint.** Explicit Close also discards the final pair if destruction needs a retry. Ordinary Stop keeps an otherwise healthy workspace and its slot until closed or safely released for waiting work under the policy above. Merge and run/account deletion remove checkpoints as before. A host/service restart still cleans up disposable workers; usable checkpoints restore saved tree/history in a fresh worker. Without a checkpoint or saved capacity-reclaimed commit, follow-ups after release/restart use the last pushed branch. The workspace grace period itself is not a backup across crashes. Deleting a run or account removes its saved API clone as well.

## Storage and development

One persistent `/data/gond-agent.sqlite` database (WAL mode) stores accounts, sessions, OIDC/provider settings, schedules, images, transcripts and usage. `/data/checkouts` holds service-side clones; `/data/container-instance` identifies this installation's disposable Docker resources. Worker volumes are temporary and are not application backups. Use a local filesystem volume, not a network filesystem, and run only one service against each data volume. Stop the service before backing up the full data volume, or use SQLite's backup API. Keep backups of the auth secret separately; OIDC and provider secrets depend on it.

API: `cd api && npm ci && BETTER_AUTH_SECRET=<random-32+-characters> npm run dev`. The process uses `BETTER_AUTH_URL=http://localhost:8787` by default. Build `web` for static serving, or run its Vite dev server. Set `BETTER_AUTH_URL` to the browser origin when testing auth through Vite. The workspace dev URL is `/agents/`. HTTP bootstrap works on a private host/LAN address; use HTTPS before exposing accounts or provider keys remotely.

Validation commands and development rules are in [AGENTS.md](AGENTS.md). CI typechecks/tests the API, lints/builds the workspace frontend, checks/tests the worker and builds both Docker targets. Only the workspace frontend enters the runtime image. Docker CI runs real container lifecycle, model relay, Git export, interruption, recovery and browser tests, including first-administrator registration, provider setup and sign-in after a restart at desktop/phone sizes on HTTP. To run the full suite locally after building both images: `cd api && GOND_AGENT_CONTAINER_TEST_IMAGE=gond-agent-worker:local GOND_AGENT_RUNTIME_TEST_IMAGE=gond-agent:local npm test -- test/containers.integration.test.ts`.

The onboarding fixture clears only persisted auth request budgets between its independent bootstrap and returning phases, while retaining accounts and application settings. Production rate limits still survive restarts; a separate regression test guards that behavior. Browser failures include bounded auth response statuses to distinguish a rejected session lookup from a rendering failure.

### Long conversations

Long conversations compact automatically near the model's context limit, including between tool rounds, and continue without another prompt. At least the last six messages stay unchanged, extending the preserved tail to keep tool calls and results together; older work becomes a summary with the current plan and explicit file paths. Histories of six or fewer messages, or a pair-safe cut of zero, make no summary request; a replacement that is not strictly smaller also reports “Nothing more to compact”. Automatic compaction skips this outcome while used context is still below the window and continues to the model, without trying again until history changes. Manual compaction, overflow recovery and automatic attempts at or above the window still fail plainly; other errors are not skipped. Failures and cancellation preserve the original history, and failed/no-progress attempts do not consume the per-turn compaction count.

For summary input only, old tool output is clipped and old images are replaced with text placeholders before summarization, without decoding or re-encoding. Oversized input is summarized in bounded chunks and merged, with at most 16 summary model requests per compaction including retries. Reaching this cap when further requests are needed fails distinctly with “Too much history to summarise in one pass”. Requests use a conservative serialized-byte bound with output and framing reserves; an unknown context window (`0`) skips the bound check and uses the default 8000-token output reserve. Normal model requests still keep only the eight newest images, independently of compaction; neither image filter changes the stored transcript.

Context overflow triggers one automatic compact-and-retry only when identified by an explicit context-overflow code or HTTP 400 with context-specific wording. HTTP 429, rate-limit codes and generic token or `max_tokens` errors are not context overflow. A turn stops with a plain error when the five-successful-automatic-compaction limit is exhausted or overflow repeats; send a follow-up or choose a larger-window model if the recent context itself is too large. The transcript keeps earlier output and shows a “Context compacted” marker after successful compaction. Task histories receive the same protection.

### Task plans

For multi-step work, the built-in runner can use `update_plan` and `list_plan`. The plan shows as a checklist in the conversation and is also available to other tools over MCP. Run lists show plan counts while work is active.

Plans stay in memory across follow-ups and compaction. The service stores `todos` events and the latest plan summary in SQLite, then restores the plan into a replacement worker when reopening a workspace or continuing after a service restart. This plan-only fallback is separate from checkpoint recovery, which restores the saved conversation and work tree when a usable checkpoint exists.

`GOND_AGENT_PLAN_REMINDER_EVERY` controls context reminders in main-worker model rounds (default `6`, `0` disables). The current bounded plan is included on the next request after a change and at the interval. `GOND_AGENT_PLAN_NUDGE_LIMIT` controls optional continuation nudges when a final response leaves pending/in-progress steps (default `2`, `0` disables, hard maximum `2` per user turn). After that cap, plan status does not delay a final response; the separate advisory evidence gate may still prompt for missing evidence. Plans are guidance, never a completion requirement or run failure condition. Set these variables in `.env` for the default Compose deployment (see `.env.example`); the API service validates and forwards them at worker startup. Invalid non-integer, negative or out-of-range settings log a warning without the supplied value and use defaults. A malformed initial plan also logs a warning and starts with an empty plan.

Remote MCP `get_session`, `list_sessions` and `read_session_events` include bounded `plan_steps`, `plan_done`, `plan_total` and `current_step`; see the [protocol](protocol/README.md#task-plan-state).

### ChatGPT plan

Each account can sign in with ChatGPT in **Settings → Models → ChatGPT plan** so the built-in agent uses that person's ChatGPT plan instead of an API key. This uses OpenAI's "Sign in with ChatGPT" token sharing for open-source apps: Gond Agent registers itself on the first sign-in as "Gond Agent", and the issued app registration is kept for that account. Plan usage counts toward the person's ChatGPT limits; review it at [ChatGPT settings → Usage](https://chatgpt.com/settings/usage). Gond Agent never switches a plan request to API billing.

Because the sign-in returns to `http://127.0.0.1:1455/auth/callback` on the computer running the browser, not on the Gond server, sign-in works by pasting back:

1. Select **Continue with ChatGPT**. A ChatGPT tab opens.
2. Approve Gond Agent. The browser then shows a page that can't load, starting with `http://127.0.0.1:1455/auth/callback`.
3. Copy that whole address from the address bar and paste it into Gond Agent, then select **Finish sign-in**.

Gond Agent only reads the pasted address and never opens it. A sign-in attempt belongs to the browser session that started it and expires after 10 minutes. The first successful sign-in shows "You're using your ChatGPT plan". A person can connect several ChatGPT accounts; each appears as its own group in the model picker, with "Using ChatGPT plan" and a **Manage usage** link next to the picker.

Tokens are encrypted in SQLite with `BETTER_AUTH_SECRET`, stay in the API service, and are refreshed there before they expire (or once after a rejected request); refresh tokens rotate and are replaced together with the access token. Workers, browsers and logs never receive them. **Sign out** revokes the session with OpenAI and clears the tokens but keeps the registration for the next sign-in; **Remove** also deletes the account entry. Deleting a Gond account signs out its ChatGPT accounts.

Plan usage is a preview with limits that Gond Agent follows: requests are not stored by OpenAI, the agent's tools are sent in a namespace, and hosted tools, sampling settings and output limits are not used. When a usage limit is reached, the composer and settings show a usage-limit card and Gond Agent pauses plan requests for that account briefly instead of retrying. If ChatGPT reports that plan usage isn't available for an account, workspace or region, Gond Agent says so and stops; it doesn't loop through sign-in again. Use an API connection in those cases.

Grok and other subscriptions are not supported. Use xAI through an API key on an OpenAI-compatible connection.

### Upgrading from Claude Code and Codex agents

Earlier releases could run Claude Code or Codex inside workspaces. These agents and their runtime installation have been removed; Gond Agent now has one backend, the built-in runner. The first start after upgrading deletes saved Claude Code and Codex sign-ins and session state (overwriting them in the database), removes their runtime records, pauses schedules that used their models, and keeps their runs readable. It then removes the pinned runtime volumes that Docker reports with this instance's labels, and orphaned workers of this instance as usual; other instances' resources are never touched. The service log lists what was removed, without secrets.

`task` can delegate an independent `reviewer` (read-only JSON findings/verdict) or `test_writer` (test-only edits and permitted test execution) without copying its working history into the main conversation. Supply the full task statement and current diff or relevant paths in `prompt`. `explore` remains a read-only investigation role. Legacy `general` and omitted kinds now select the scoped test-writing policy, not unrestricted changes. Reports are bounded, framed as untrusted advice and must not be followed as instructions; review is optional, not a completion gate.

The single typed role table enforces four call slots per parent worker lifetime: three general-purpose calls shared by all current kinds plus one reserved for a future reviewer kind (unavailable to current `task` calls). Other bounds are two concurrent children, depth one, 48 rounds/128 tool calls/180 seconds per child (queue time included, up to one second cancellation cleanup), 2048 requested output tokens per response, an independent 128 KiB response guard, and an 8192-byte report cap. Follow-ups retain the allowance; checkpoint export/import preserves the counter. Parent cancellation cancels children. Children never receive delegation, network, unrestricted shell, MCP or parent-state controls; they retain the parent's Plan/Ask restrictions even if it later switches to Allow. Test edits resolve paths and check all patch sources/destinations against an explicit repository test allow-list. `test_writer` is equivalent to “can run arbitrary repo code”: it writes a test and runs the test command. The write allow-list and exact commands bound the tool, not the code; permission modes still apply (Plan denies, Ask asks). Execution uses the existing foreground permission and environment-scrubbing path; the container remains the boundary. Service recovery/import preserves consumed allowance from the checkpoint; fresh or fallback workers without import start at zero. This is not an exactly-once durable delegation ledger. Service and runner compatibility epoch `gond-agent-checkpoint-4` retains epoch 2's bounded counter semantics and rejects epoch 1's unrestricted ID counter. Service recovery also admits the latest authenticated epoch-2 sealed pair with absent/null `evidence`, keeping its original storage/claim key and requiring matching payload/row/envelope versions. The runner upgrades it only in memory; the next normal epoch-4 paired save transactionally consumes the predecessor. Epoch-2 ledgers and future epochs remain rejected, with no ciphertext/row relabeling or search of older checkpoints. The runner state schema and service continuation-ledger format are unchanged. Recovery adds an additive finishing-phase marker and claim-lease/quarantine metadata.
