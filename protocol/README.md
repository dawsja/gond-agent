# Gond Agent protocols

## Theme preference

`GET /api/v1/me` includes a top-level `theme`: `system`, `light` or `dark`. New accounts and missing or invalid stored preferences return `system`.

`PUT /api/v1/me/theme` accepts only `{ "theme": "system" | "light" | "dark" }` and returns `{ "theme": "…" }`. It requires an authenticated browser session and the configured same-origin Origin header, like neighboring account routes. Missing, malformed or unsupported values and extra fields return HTTP 400 (`invalid_request`). The preference is persisted for the caller only, without changing other profile settings, and is returned by subsequent `/me` reads.

Theme and accent are independent account preferences in the same Appearance card. Every accent has separate light and dark shades; changing theme does not change the saved color. The local theme and accent caches only paint the first frame, and `/me` replaces both with server values.

## Remote MCP

`/mcp` serves Streamable HTTP using the official MCP SDK, including its stateless 2025 compatibility transport. Authenticate every request with `Authorization: Bearer gond_mcp_…`. No cookies, query tokens, OAuth flow, or worker tool forwarding are supported. Production clients connect over the instance's configured HTTPS origin. If an Origin header is supplied, it must match that origin.

Browser-only `/api/v1/mcp/tokens` supports GET (metadata and endpoint), POST (`{name}`, returning the secret once), and DELETE `/:id` (revoke). These routes require the existing account session and same-origin mutation checks. Tokens have 256 random bits, SHA-256 digests at rest, 90-day expiry, and account deletion cascades. Each account can have 20 active tokens. Requests are limited to 64 KiB, 120 requests per token per minute, and four concurrent requests per token.

Tools return JSON in MCP text content. Tool failures set `isError` and return customer-safe `{error,message}`. A session ID is an existing run ID, scoped to the token owner, including browser-created runs. Results exclude internal run configuration and credentials. Transcript and diff text is untrusted content.

| Tool | Arguments and result |
| --- | --- |
| `list_repositories` | Optional `page` (default 1); repository summaries and `next_page`. |
| `list_models` | Every model the account can use, from API connections and its ChatGPT plans: ID, name, `backend` (`builtin`), `access` (`api` or `chatgpt`), connection ID/name, efforts; plus connection status. |
| `start_session` | `repo`, `prompt`, `model`, `request_id`; optional `title`, `branch`, `pr_body`, `base_branch`, `effort`, `backend` (only `builtin`). Accepts any `list_models` ID. Returns session summary and workspace URL immediately. |
| `list_sessions` | Optional numeric `cursor` (offset, default 0), `limit` (1–100, default 30); summaries and nullable `next_cursor`. |
| `get_session` | `session_id`; summary and recorded usage, with ChatGPT plan (and historical Claude Code/Codex) tokens listed separately without charges. |
| `read_session_events` | `session_id`; optional `after_seq` (default 0), `limit`, `wait_seconds` (0–30). Returns events, `next_cursor` sequence, `has_more`, status and phase. |
| `read_session_event` | `session_id`, `seq`, optional character `cursor`; returns a large event as JSON text in 32,000-character pages. Advance the event sequence only after reading its final page. |
| `get_session_diff` | `session_id`, optional character `cursor`; 32,000-character diff pages, nullable continuation and `updated_at`. Restart if the revision changes. |
| `send_session_message` | `session_id`, `text`, `request_id`; optional `pr_body` (persistent override), `model`, `effort` (any available model). Sessions of the removed Claude Code/Codex agents return `retired_backend`. |
| `close_session` | `session_id`; cancel capacity-queued work, or save and push idle/stopped workspace changes, then release capacity. Refuses busy live workspaces; preserves history and resumes from pushed branch on follow-up. |
| `stop_session` | `session_id`; cancel capacity-queued work, or interrupt the turn without destroying a live workspace or freeing its slot. |
| `open_session_pull_request` | `session_id`; open or return its existing PR. |

Event pages contain at most 128,000 JSON characters; oversized individual events return a `large_event` reference instead of silently losing transcript content. Reads revalidate access while waiting and before responding. Disconnecting a read does not stop execution. Lists and diffs reflect live state rather than a snapshot.

`start_session.title` is optional plain text without newlines, at most 120 characters, used for the run, commit and PR titles. Optional `branch` must match `^(gond-agent|feat|fix|chore|docs)/[a-z0-9][a-z0-9._-]{0,80}(/[a-z0-9._-]{1,80}){0,3}$`; `..`, trailing slash, `.lock` suffixes and protected names `main`, `master`, `HEAD`, `release*` and `v*` are forbidden. An existing remote branch is refused unless it belongs to this run. Explicit branches are rechecked before first publication, and a create-only Git lease prevents overwriting a branch created after that check.

Optional `pr_body` on `start_session` and `send_session_message` is plain text up to 20,000 characters; follow-up overrides persist. PR body precedence is explicit `pr_body` (including an empty string), otherwise clean main-agent final text after the last tool call, otherwise the plain run title, never the prompt. Only `end_turn` (the runner's normalized clean stop) qualifies; truncated, refusal/filter, unknown, compacted, interrupted and error stops do not. Failed/stopped runs and successful turns with no final text use the title. Commentary and subagent text never supply the fallback. This publication selection leaves the live event transcript unchanged. MCP session reads and workspace run reads expose both the nullable `pr_body` override and the chosen `description`; the workspace PR panel renders that description.

Start and follow-up `request_id` values are 1–100 characters, token-scoped and persisted across restart. Retry with identical arguments; changed arguments conflict. Start reserves a stable run ID before asynchronous work; run insertion and initial queueing are atomic. A start retry returns the existing owned run's current state and queue position, never another run. Follow-up enqueue and result persistence are atomic. Sessions retain `source: "mcp"` and token ID attribution. No billing fallback, direct shell/file access, merges, account deletion or image input tools are added.

Retention keeps all request records for valid tokens. Scheduler cleanup removes records for invalid tokens and deletes token metadata 30 days after expiry or revocation. Schedule claims older than 30 days are removed unless they match a schedule's current occurrence.

## Model requests

Authenticated workspace run-list/detail reads refresh only their account's linked PR metadata using read-only GraphQL batches of up to 25 PRs, a 30-second cache and a five-second request limit. Missing/unavailable metadata preserves the last known state. `run.pr` can carry optional `state: open|closed|merged`; display updates the existing PR card. External merges mark idle runs merged and close their workspaces; active/queued work finishes before finalization. Follow-ups to known merged PRs are rejected. The scheduler does not perform GitHub polling.

The workspace normalizes tool names and structured arguments only for display. Stored `tool.start` events keep their original identities and inputs. Consecutive local exploration and file edits render as expandable groups; external MCP calls retain connection identity in details. Completion and failure labels follow observed tool status, without generating additional agent prose or treating completion as proof that a check passed.

ChatGPT plan models do not require API connections. Provider settings accept an empty `connections` array with an empty `defaultModel` to remove all API providers. Empty Settings remain empty after reload; first-time API setup offers an unsaved draft. Composer discovery messages are scoped to the selected API connection; ChatGPT plan selections show "Using ChatGPT plan" with a Manage usage link and, when limited, a usage-limit card instead of API connection warnings. With no selectable model, API discovery failures remain visible.

The internal container worker calls `GET /v1/models` and `POST /v1/responses` through its loopback proxy at 127.0.0.1:8787. The service receives those requests over Docker's attached stdio channel and scopes them to that run; no network-facing model/control ports or provider keys are needed inside workers. Schemas: `api/src/wire.ts` and `runner/src/api/wire.rs`. Model responses use SSE (`event: <name>`, `data: <JSON>`): response/block starts, block deltas/ends, errors, and response.end with token usage and a stop reason. Opaque reasoning blocks retain their provider and connection-scoped model identity. Provider API URLs, formats, encrypted keys and model IDs live in SQLite; only administrators can edit them. The service translates to Anthropic Messages, OpenAI Chat Completions or OpenAI Responses and sends keys only to the configured endpoint.

Every loopback request (including catalog, image-bearing responses, retries and `/v1/search`) carries `Authorization: Bearer <token>`. The container control service generates `secrets.token_urlsafe(32)` at worker start and supplies it only through `Popen(env=...)` as `GOND_AGENT_RELAY_TOKEN`; it never enters argv, logs, control frames or the API's state. The relay checks it with `hmac.compare_digest`, returning generic 401 for missing/wrong credentials on every method/path. With valid credentials, any Origin header or a Host other than `127.0.0.1:8787` / `localhost:8787` returns 403, and a POST without `application/json` returns 415. The runner sends no Origin and follows no redirects. Workspace subprocess environments and MCP expansion omit the token; subagents reuse the authenticated client. This is protection against hostile web pages, not agent-executed code: same-UID code can read the runner's initial environment through `/proc/<pid>/environ`. The container remains the boundary. API-to-control-service trust over Docker stdio is unchanged; forwarded model frames contain only method, path and body, not the bearer header.

## Checkpoint controls (foundation)

These internal controls are implemented; checkpoint scheduling and RunService recovery are **not yet integrated**. Existing run statuses and restart behavior remain unchanged. The planned additive `interrupted` state (including checkpoint age), `run.interrupted` and `run.resumed` events must be added to HTTP/MCP/UI together with transactional resume claims; they are not emitted by this slice. Never-started queued runs must remain queued across restart.

The Docker controller accepts these separate RPC methods:

| Method | Input / result |
| --- | --- |
| `checkpoint_tree` | `base_sha`, connected-owner `identity:{name,email}` → base64 `bundle`, `base_sha`, `head_sha`, `checkpoint_sha`. |
| `restore_checkpoint` | The above bundle and **trusted persisted** revision pins → validated pins after tree-only application; worker must not be running. |
| `export_state` | `run_id`, `owner_id` → `{state:…}` at a safe runner round boundary. |
| `import_state` | `run_id`, `owner_id`, `state` → `true` after strict validation in a fresh idle runner. |

Tree export uses an isolated repository and temporary `GIT_INDEX_FILE`, `add --all` honoring `.gitignore`, `commit-tree`, and exactly `refs/gond-agent/checkpoint`. It changes neither clone HEAD/index nor branch, and does not publish. The bundle requires the saved HEAD; the pinned original base must also already exist in the clone. Restore caps base64 before decoding, verifies refs/prerequisites/objects in a throwaway repository with hooks/fsmonitor disabled and fsck enabled, validates pins and parent, checks paths, and applies a binary tree patch inside the worker only. Failure is an error seam: the eventual orchestrator must discard a partially restored worker and fall back to the last pushed branch. Compressed bundles are capped at 64 MiB, not their expanded size; worker resource limits still apply.

Staging metadata is not restored. Newly staged ignored files reject export rather than being silently omitted or lost at publication; ordinary ignored untracked files remain excluded. The real index is read only to detect this unsupported case, using the same isolated Git configuration.

Runner JSONL uses `export_state {request_id,run_id,owner_id}` and `import_state {request_id,run_id,owner_id,state}`. Replies are `state.exported {request_id,state}`, `state.imported {request_id}`, or `state.error {request_id,operation,code}` with fixed safe codes. These are **control frames, never transcript events**. The controller generates correlation IDs, bounds in-flight controls, drops late/unsolicited/stale replies, caps state at 4 MiB and filters all `state.*` frames from ordinary event reads. Generic `send` rejects state controls. See [runner/CHECKPOINTS.md](../runner/CHECKPOINTS.md) for schemas, error codes and admission rules.

The controller's 120-second state RPC deadline covers pipe backpressure and the reply wait. Reply waiting releases the worker lock so interruption remains possible. A failed pipe write may leave an incomplete JSONL frame: the controller kills that worker's process group, revokes its relay credential and requires a fresh worker rather than reusing the stream. A reply timeout alone does not kill the worker; late control frames are filtered out.

State schema version 1 / runner compatibility epoch `gond-agent-checkpoint-1` contains run/owner binding, stored `history`, `plan` and counters (subagent ID, context estimate, plan cadence/nudges and turn-compaction budget). The summary is preserved in stored user-role history. This is not a `ResponsesRequest`: old images are not removed. Only user/assistant/tool roles are allowed, nested schema fields are strict, tool rounds must pair fully and images are normalized on import. Import does not run a model or restore processes, tools, subagent histories or pending questions. Export waits through streaming/tools/compaction/questions to a safe main-round boundary. The caller must coordinate the matching tree snapshot before allowing further tool mutations; merely exporting state then snapshotting a changing tree is insufficient.

The API storage module stores opaque bundles and auth-secret-sealed state in private, atomically published files with SQLite metadata. The bundle is **not encrypted**; the API data volume is its trust boundary. Save requires base/HEAD/checkpoint SHA pins; load verifies those sealed pins, owner/run/version, creation time and bundle digest, but bundle structural validation belongs in the worker. The module is not constructed by production RunService yet. Application deletion/retention hooks and startup construction must be wired before checkpoint persistence is enabled.

CI handoff seam: PR #22's CI loop is not on this base. Before a future release-after-push, save a coordinated checkpoint; import it on the CI-fix reopen so earlier conversation survives. Keep the default CI-fix-round flip behind a named constant for Board review; this foundation does not change that default.

## Agent events

Worker stdin accepts newline-delimited JSON: `user` with text and inline base64 image bytes (the service resolves owner/run-scoped upload IDs before sending), `interrupt`, `compact`, and model/mode/skill controls. Output is newline-delimited JSON: session.start, turn.start/end, text.delta, reasoning.delta, stream.reset, tool.call/start/output/images/end, todos, agent.spawn/status/end, usage, compacted and error. Main-agent events use `agent_id: main`. The container worker runs autonomously with all tools allowed inside its workspace. Agent schemas live in `runner/src/agent/events.rs`. Additive `tool.call {agent_id,call_id,name}` marks every dispatched tool call, including internal, invalid and cancelled calls, before dispatch. It clears the main reply candidate without adding visible transcript activity or requiring `tool.end`; historical `tool.start` events remain reply boundaries too. Only a main `turn.end` with `stop_reason: "end_turn"` and no main-agent error marks the collected text as a publishable final reply. The runner receives clean provider stops normalized to `end_turn`; no other stop reason qualifies. Older unmarked summaries fall back to the plain run title, never the prompt.

`stream.reset {agent_id,text_length,reasoning_length}` rolls back deltas from a failed model-request attempt before retrying. Lengths count UTF-16 code units (JavaScript string lengths), separately for text and reasoning, across all blocks in that attempt. Consumers remove those suffixes only for that agent; completed earlier responses, tool activity and other agents remain intact. The runner emits one reset per discarded attempt with nonempty text or reasoning output, before any retry deltas, and none for retries before output, terminal failures or interruption. Resets are persisted/replayed in order with deltas; the workspace transcript and run summary discard partial text so the successful reply appears once. Partial tool calls never execute or enter model history.

### Context compaction

The main loop and task histories compact before turns and between completed tool rounds at 85% of the configured context window. Provider-reported usage plus newly appended tool results and a history-size estimate drive the threshold. History estimates apply the same newest-eight image filter as request serialization, without decoding images. Each turn permits at most five successful automatic compactions total, including overflow recovery; failed or no-progress attempts do not consume this count. Exhaustion returns a plain error; it is not a tool-round or run-lifetime budget. A context-overflow request gets one compaction and one retry; a second overflow fails plainly. Recognize overflow only by an explicit context-overflow error code or HTTP 400 with context-specific wording. HTTP 429 and rate-limit codes are never context overflow; generic token or `max_tokens` errors are insufficient. Ordinary retryable network/provider failures retain their existing retry policy.

Compaction summarizes the older prefix while keeping at least the last six messages verbatim. The cut moves backwards to avoid separating tool calls and results. Histories of six or fewer messages, or a pair-safe cut of zero, issue no summary request and report “Nothing more to compact”. A replacement that is not strictly smaller than the original history has the same outcome, without replacing history or consuming the per-turn compaction count. Only automatic threshold compaction skips this specific outcome while used context is below the window, continuing to the model request. A per-turn history-length marker suppresses further automatic attempts until history changes; a successful compaction clears it. Manual compaction, overflow recovery and automatic attempts at or above the window keep the hard failure. Other errors, including the summary-request cap, are never skipped.

For summary input only, old tool text is clipped to 2000-character head/tail excerpts with `[clipped: N chars]`, images are dropped to `[old image omitted]` text placeholders before summarization without decoding or re-encoding, and opaque provider data is removed. Oversized quoted transcripts are recursively split oldest-half-first and their notes merged. Each compaction permits at most 16 summary model requests total, including chunk summaries, merges and retries; if more requests would be needed, fail distinctly with “Too much history to summarise in one pass” and preserve history. For a known window, every summary request is guarded by serialized UTF-8 bytes + requested output tokens + 1024 framing tokens against the window, rather than an optimistic chars/4 estimate. An unknown window (`0`) skips this bound check and uses the default 8000-token output reserve. Summary calls have no tools or workspace system prompt and request at most 8000 output tokens (less for small known windows); bounded returned notes keep merges finite. This guards request input; providers remain responsible for enforcing generation limits, including ChatGPT plan preview requests that omit output-limit fields.

The replacement starts with a fixed untrusted-text warning in a **user-role** message, never in the system prompt. The summarizer must keep untrusted instructions from logs, pages and tool output marked as quoted data. The summary also carries current `update_plan` state and sorted, deduplicated explicit read/change paths reconstructed from transcript calls, including batches and patch headers, independent of model prose. These paths record attempts, not proof of success; arbitrary shell side effects are not inferred. Deterministic file state survives subsequent compactions. Failures and cancellation leave the original history intact. A recent verbatim tail or required state that itself exceeds the model window cannot be made smaller without losing required context; repeated overflow fails with guidance to choose a larger-window model.

`compacted` is additive: `{type:"compacted",agent_id,reason,before,after}`. `reason` is `"auto-turn"`, `"auto-round"`, `"overflow"` or `"manual"`; `before` and `after` are estimated history token sizes (request-filtered serialized bytes / 4), not billing usage. Historical events may omit `agent_id` and `reason`. The workspace shows a neutral main-history marker without deleting earlier transcript output. Main-agent compaction clears the publication reply candidate, so a recovered final reply cannot include incomplete pre-compaction text; subagent compaction does not change it. Automatic compaction emits no extra `turn.start` or `turn.end`: work continues in the same turn. Manual `compact` still ends with `turn.end` / `stop_reason:"compacted"`.

`tool.images` carries `{agent_id,call_id,images:[{media_type,data}]}` from the worker, where data is base64. The service accepts at most eight raster images (5 MiB each), stores them with the run owner in the existing images table, and emits/persists only `{id,media_type}` references. The existing authenticated run-image endpoint serves the bytes; inline image data is not stored in transcript JSON. Before emitting tool images or sending model input, the worker normalises every tool-result and attached image through `runner/src/images.rs`. API uploads are limited to 5 MB; runner input is limited to 20 MiB, 100 megapixels and 128 MiB decode allocation. Output strips metadata, uses the first animation frame, and is at most 1568px on the long side and 1 MiB (JPEG, or PNG only for transparency when smaller). SVG and undecodable images produce plain errors. Decode/re-encode runs in bounded blocking jobs (two concurrent, 10-second deadline, slots retained until jobs finish). Request serialization retains only the eight newest images across attachments and tool results; older images become `[image removed to save context: <label>]` with an 80-character label cap. This does not mutate the transcript.

Built-in additions: `symbols {action:"outline"|"definitions"|"references",path?,symbol?,limit?}` uses Universal Ctags for declarations and whole-identifier lexical matching for references (not semantic/LSP resolution). Searches cap files at 5000, skip files over 1 MB and honor ignores. `batch {calls:[{tool,input}]}` runs 1–8 independent built-in read calls, retaining order and per-result labels/errors; only read, list_directory, glob, grep, symbols and bash_output are allowed. `browser {url,script}` executes a Playwright test body with page/expect at wide and phone sizes; it is an execution tool, unavailable to read-only explore agents and blocked in plan mode. Chromium runs headlessly without its own sandbox; the non-root, limited container is its containment boundary, not a separate kernel.


## Container control

Before container startup, the service makes a depth-one, single-branch, tag-free checkout using command-scoped GitHub credentials. Resumed runs clone their saved run branch and shallow-fetch the pinned original base SHA for cumulative diffs; no full Git history is transferred. `run.status.step` distinguishes cloning (including rate-limited, sanitized download/checkout percentages), packing, container startup, loading the checkout, and agent startup. Compressed checkout archives are bounded to 128 MiB before base64 encoding; oversized archives fail with `repository_too_large` rather than exceeding controller frames. Clone/packing errors are plain customer messages; technical subprocess details remain in service logs.

`ContainerPool` creates a labeled per-run bridge network, workspace volume, tools volume and non-root container from the operator-selected worker image (default `ghcr.io/dawsja/gond-agent-worker:main`). Compose pulls this image alongside the runtime; its one-shot image helper exits without starting the controller. Limits default to 2 CPUs, 2 GiB RAM, 512 processes and 256 MiB shared memory. The root is read-only; home and /tmp are writable `nosuid,nodev,noexec` tmpfs mounts. A separate per-run UID-1000-owned executable named volume at `/opt/gond-tools` holds installed toolchains outside the checkout. The image configures installer homes, uv tool/managed-Python directories, XDG data and PYTHONUSERBASE in the tools volume and appends its bin directories (including Python user scripts) after the image PATH to avoid shadowing image commands; the controller and runner preserve that environment for Bash calls. TMPDIR/TMP/TEMP/TEMPDIR point at `/opt/gond-tools/tmp`, created with UID 1000 ownership in the image and recreated before worker startup. XDG_CACHE_HOME and Bun/npm/pip/uv caches live under `/opt/gond-tools/cache`, not the 256 MiB home tmpfs; these executable scratch/cache directories are removed with the tools volume. CARGO_TARGET_DIR stays unset (repo-local targets), and explicit PLAYWRIGHT_BROWSERS_PATH and NODE_PATH remain unchanged. Bun 1.4.4 (lockfileVersion 2 support) and uv ship pinned with SHA-256 verification in the image; packageManager does not trigger a network version switch. Rust can be installed per run. Tools are never shared across runs/users and are removed when the workspace is released, including failed-work retention expiry, explicit close and recovery. Neither named volume is disk-quota-limited. Ordinary Docker disk-backed volumes do not expose per-mount `nosuid,nodev` flags; scratch retains those flags. Noexec is defense in depth, not an execution boundary: interpreters already execute arbitrary code. Native tools increase the kernel syscall attack surface inside the existing seccomp-filtered container. All capabilities are dropped, privilege escalation is disabled, Docker's default seccomp policy remains enabled, and no host paths, credentials, devices, Docker socket or published ports are supplied. Containers share the Docker host kernel; network separation does not deny host/LAN egress. Operators should use a dedicated host and suitable egress policy.

The service attaches stdin/stdout with `docker start --attach --interactive`, with no TTY. Newline-delimited JSON requests `{id,method,...args}` receive `{id,result}` or `{id,error}`. Methods: ping; setup (base64 repository tar archive, extracted with Python's data filter); start (model); send (AgentInput); events (zero-based after cursor, at most 200 events and approximately 16 MiB per batch, allowing one larger image event); snapshot (requires `{identity:{name,email},title?}` resolved by the service; commit as that author and committer with hooks/signing disabled and return base64 git bundle and HEAD); diff. A frame is limited to 256 MiB. Worker stderr stays in /tmp/worker.log; control errors go to service logs, not ordinary customer messages.

Model traffic shares that channel: the controller emits `{model:{id,method,path,body}}` (body is base64), and the service replies with `{model_id,status,headers}`, zero or more `{model_id,chunk}` frames (base64 bytes), and `{model_id,end:true}`. HTTP/SSE chunks are forwarded incrementally with backpressure. `{model_cancel:id}` aborts a disconnected request. Only GET /v1/models and POST /v1/responses are accepted. The run scope is bound by the service closure, not by credentials supplied to the worker.

On stdin EOF or termination, the controller stops its worker. Cleanup removes containers before their volumes/networks and is idempotent. Recovery sweeps only resources bearing this installation's `io.gond-agent.managed`, `io.gond-agent.instance` and optional `io.gond-agent.run` labels. The random instance identity persists in /data/container-instance; do not run multiple services against the same data directory.

## Workspace API

Authenticated `GET /api/v1/me` includes `user.image`, `user.has_photo`, top-level `accent` (default `blue`), and `automations:{auto_pr}`. `PUT /api/v1/me/accent {accent}` returns `{accent}` and saves only the signed-in account's preference. It requires the same session and configured Origin as other `/me` mutations; malformed bodies, extra fields and values not accepted by `shared/accents.ts` receive 400. The shared module defines the ordered choices and labels; the dark-only workspace applies the five CSS tint tokens using `<html data-accent>`. The `gond-agent-accent` localStorage value is only a first-frame hint; `/me` always wins. Failed saves roll back the optimistic color and show an error toast. `PUT /api/v1/me/automations {auto_pr:boolean}` rejects retired polling preferences. The scheduler only executes saved schedules and retention cleanup; it does not poll GitHub issues, checks or pull requests. Existing historical events remain stored, but no issue/check-triggered messages are generated.

Authenticated `GET /api/v1/me/deletion` returns `{last_account,has_password,blocked_reason}` without caching. Same-origin `DELETE /api/v1/me {confirmation:<exact account email>,password?:string}` deletes only the signed-in account after the Settings confirmation modal. Password accounts require Better Auth password verification; passwordless accounts require a session created within 15 minutes. Attempts are bounded to five per account per 15 minutes. Active runs and deletion of the last administrator while other users remain return 409. Account changes are serialized with authentication callbacks/registration; pending run creations cannot recreate deleted account data. Idle containers and scoped checkout caches are closed/removed first. Better Auth removes the user, credentials and sessions; a SQLite trigger atomically removes owned records, including retained/deleted runs and scheduled occurrence claims. Final-account deletion also clears provider/GitHub/OIDC connections and resets in-memory auth, model discovery and device-login state. The response is `{ok:true,setup_reset:boolean}` with expired auth cookies and `Cache-Control:no-store`. Native `/api/auth/delete-user` remains disabled so it cannot bypass the workspace safeguards. The browser reloads `/agents/`; an empty instance reopens administrator registration, then provider setup.

`PUT /api/v1/me/photo` accepts up to 2 MiB of PNG/JPEG/WebP bytes for the current account. Bounded decoding rejects images above 16 megapixels and SVGs; the server strips metadata, resizes/circular-masks the result to a 256px PNG, and stores it in `profile_photos` with a fresh revision. The response is `{image,has_photo}`. `DELETE /api/v1/me/photo` removes only the current account's upload. Authenticated `GET /api/v1/users/:id/photo?v=<revision>` serves matching images with `image/png` and `Cache-Control: private, no-store`; stale revisions and absent photos return 404. Account deletion cascades to uploaded photos. The browser uses a round crop preview, supports repositioning/zoom, and submits the cropped PNG. Enter sends new tasks/follow-ups; Shift+Enter inserts a newline and IME/key repeats never submit.

Authenticated `GET /api/v1/github` returns `{configured,login,managed}` without credentials; `managed` means the current user has a saved personal connection. Every user can `POST /api/v1/github/login` to start gh device authorization. `GET` returns `{status,id?,code?,url?,expiresAt?,message?}` with `Cache-Control: no-store`. Concurrent flows are keyed by account; only the initiating session sees the code. Another session of the same account sees `busy`/`idle`; another account can start independently. `DELETE /api/v1/github/login {id}` cancels only the matching initiating flow. Codes expire after ten minutes, output/active-flow counts are bounded, and cancellation/expiry/shutdown kill authorization subprocesses. Approval requires the initiating session to remain valid. `DELETE /api/v1/github` cancels pending authorization and deletes the personal sealed token.

Administrator-only `/api/v1/settings/github` supports `GET {configured,login,managed,fallback}`, `PUT {fallback:boolean}` and `DELETE` of the shared token, with device-flow endpoints at `/api/v1/settings/github/login`. `github_connections` stores sealed personal tokens by `user_id`; `settings.github` retains the shared token and `settings.github-shared-fallback` stores the opt-in. Additive transactional migration enables fallback once when a shared token, non-empty service GH_TOKEN/GITHUB_TOKEN, or GH_CONFIG_DIR containing a non-empty hosts.yml already exists (the same hasServiceGithubCredentials predicate used at runtime); installs without either default off. Later administrator choices survive restarts. Account deletion cascades personal connections; upstream OAuth grant revocation remains in GitHub settings. Credentials resolve through `githubEnvFor`: owner's personal → shared if fallback enabled → explicit service GH credentials only if fallback enabled → 409 `github_required` (“Connect your GitHub account in Settings > Connections”). Routes use the session user, runs/publication/commit identity use the run owner, schedules use their owner, and **MCP sessions use the bearer token owner's connection**. Tokens are never returned to browsers/workers or written into checkout configuration. PR refresh batches and its 30-second cache are owner-scoped.

Administrator-only `GET /api/v1/settings/people` returns `{people:[{id,name,email,admin,methods}]}` without credentials. `PUT /api/v1/settings/people/:id/role {admin:boolean}` changes roles in a transaction and refuses removal of the last administrator (409); it serializes with signup/deletion. `GET /api/v1/me/sign-in-methods` lists the session user's methods and configured OIDC provider. Better Auth `/api/auth/link-social {provider:"oidc",callbackURL,errorCallbackURL}` explicitly links the verified ID token subject; `/api/auth/unlink-account {accountId}` unlinks only an owned method while another remains. Both require a signed-in session created within ten minutes; the guard decodes and normalizes path case, duplicate/trailing slashes and dot segments before matching on every HTTP method. Better Auth requires verified email or a trusted provider for linking. Implicit email-based linking is disabled, identities attached to another user are rejected, and new OIDC signup still follows `ALLOW_SIGNUP`.

The server root redirects to `/agents/`; only the workspace frontend is packaged and served. Public `GET /api/auth/bootstrap` returns `{firstAccount,signupAllowed,providers}` with `Cache-Control: no-store`. An empty instance shows first-administrator registration, then authenticated provider setup; existing instances show sign-in or their workspace. This public hint does not authorize registration: the serialized signup handler and database hooks enforce first-account-only registration when signup is closed.

The browser authenticates with Better Auth same-origin cookies. Email/password flows and OIDC callbacks use `/api/auth/*`. Instance configuration and run actions use `/api/v1/*`; state-changing actions require the configured Origin. OIDC settings are administrator-only and omit secrets from reads. Provider connection IDs are non-secret random UI identifiers generated with `crypto.getRandomValues`, which is available during private HTTP bootstrap.

Saving provider settings requires named connections with API formats, URLs and optional keys, not a selected model. The UI groups `openai` and `openai-responses` under an OpenAI button, with the protocol choice in Advanced settings; the Anthropic button selects `anthropic`. Names default to the provider label and may be overridden in Advanced settings. URLs are prefilled and editable through Edit URL. Saved formats remain unchanged unless explicitly edited. Clear key stages `clearKey:true` with an empty `apiKey`; Undo cancels that flag, and entering a replacement cancels pending removal. The existing PUT remains the commit point. Connections default to automatic discovery; `models` are optional manual capability/ID overrides and `discover:false` disables listing for that connection. Provider settings contain `connections` and an optional instance `defaultModel`; Auto falls back to the first available model.

Authenticated `GET /api/v1/models` powers agent and scheduled-run model pickers. It discovers `/models` on every configured connection concurrently, rejects redirects, and bounds Anthropic pagination to five pages and 500 unique models. Responses contain `{models,connections:[{id,name,status,message?}]}`; each model includes its connection ID/name and an encoded connection-scoped model ID. Supported status values are `ready`, `empty`, `unsupported` and `error`. One failed connection does not hide healthy connections or manual overrides. Catalogs and in-flight requests are shared per instance/database for 60 seconds and invalidated by URL, format, key or discovery-mode changes. `?refresh=1` refreshes with a five-second minimum interval. Cached metadata may remain usable during a temporary listing failure, but never after the corresponding connection's credentials change. Keys, provider URLs and upstream error bodies are not returned in the catalog. Run creation, scheduling and the model relay resolve the chosen connection-scoped ID, including on a cold service restart.

A run starts with `POST /api/v1/runs {repo,base_branch?,model,prompt,images?,title?,branch?,pr_body?}`. Optional `title`, `branch` and `pr_body` use the same validation and publication rules as MCP `start_session`; workspace follow-up messages accept a persistent `pr_body` override just like `send_session_message`. Messages, stop, pull creation, merge and deletion are scoped to the authenticated owner. Upload images first to `/api/v1/images`. Run status: queued, working, ready, failed, stopped, merged. A one-use ticket from `POST /api/v1/runs/:id/ticket` opens `/ws/runs/:id?ticket=...&after=<seq>`. Replay resumes after a persisted sequence number. Events carry seq and ts; run.info describes live status without becoming a transcript row. A ping gets a pong. Tickets expire after one minute and are consumed on use.

### Persistent workspace queue

Admission counts distinct live plus booting workspaces against `MAX_ACTIVE_RUNS`, including retained ready/idle/stopped/model-failed live workspaces. Browser/HTTP creates, MCP `start_session` and closed-workspace follow-ups validate before queue admission. When capacity is unavailable, accepted work waits durably instead of requiring caller retries. Queue sequence and pending work survive service restart; interrupted working runs retain the existing failed recovery behavior.

Drain FIFO within each account, selecting the account with the fewest occupied workspaces first. New admissions must not jump waiting work. Drain on capacity release, admission and startup, with a 60-second safety net; reads/polling are not required to start accepted work. Scheduler `source: runner` (also `schedule` supported) is excluded from the queue and its bounds: scheduled runs fail fast with `run_limit` at capacity or whenever the queue is nonempty and never jump waiting work. Later scheduler ticks may retry, but scheduled runs can be refused for a long time while the queue remains nonempty.

HTTP run get/list/event reads and MCP `get_session`, `list_sessions` entries and `read_session_events` expose additive `queue_position` and `queue_length` while waiting. Position is 1-based relative FIFO order among **only the caller account's queued runs**; length is that account's queued-run count. Neither reveals global queue size/order or guarantees the actual start rank across accounts. Live run events include `run.queued {position,length}` on admission and queue updates, with the same account-local semantics, and `run.dequeued` when leaving the waiting queue. These are service run events, not worker protocol controls.

Configuration accepts positive integers: `GOND_AGENT_QUEUE_MAX` (default 50 total waiting runs), `GOND_AGENT_QUEUE_MAX_PER_ACCOUNT` (default 10), and `GOND_AGENT_QUEUE_WAIT_HOURS` (default 24). Exceeding either queue bound returns HTTP 429 `queue_full` with message "Too many runs are waiting. Try again later." MCP reports the same customer-safe error code/message through its tool-error contract. Expiry fails waiting work with a plain message after the configured wait; it imposes no time budget on an active workspace.

Per-run message request-ID receipt rows grow by one small row per accepted message and remain for the life of the run, including after processing; they are deleted with the run. This is separate from the token-scoped MCP retry-record retention described above.

Stop cancels capacity-queued work; close/remove also cancels waiting. Stop remains nondestructive for healthy live workspaces and does not free their slots. Close saves/pushes retained workspace changes before freeing capacity and automatically starting waiting work; publication failure retains the workspace. Exception: stopping or closing still-kept failed work releases it immediately and discards unpushed work, as described below.

## Backend, model access and effort

There is one backend, the built-in runner (`backend: "builtin"`). Run creation, loading, saving and follow-ups check it: `POST /api/v1/runs`, schedules and MCP `start_session` reject any other `backend` with 400 `invalid_backend`, and model IDs of the removed agents (`cli-codex:…`, `cli-claude-code:…`) return 404 `retired_model`. Runs created by Claude Code or Codex before the upgrade load with `backend: "builtin"` and `retired_backend: "claude-code" | "codex"`; their transcripts, diffs and pull requests stay readable, and messages to them return 409 `retired_backend`.

Catalog model entries include `backend`, `access` (`"api"` or the subscription, currently `"chatgpt"`), `connection_id`, `connection_name`, `efforts` and optional `resolved_model`, the exact upstream ID. API model IDs are `<connection>:<encoded model>`. ChatGPT plan model IDs are `chatgpt.<account>:<encoded model>` and belong to the signed-in Gond account that owns that ChatGPT account; they never resolve for anyone else. Catalog connections include `access`, and for ChatGPT accounts `limited` and `usage_url`. Claude IDs are formatted generically without a version map; provider-advertised full names and custom labels are preserved. Missing resolution metadata never supplies an invented version.

Runs and schedules accept optional `effort` (`default`, or a model-advertised effort). Runs persist their resolved model ID and effort. Explicit unsupported effort choices return 400. Unknown API models use provider defaults unless an administrator configures capability overrides. Worker startup accepts `GOND_AGENT_EFFORT`; JSONL `effort` controls apply to subsequent requests. Model and effort controls precede each user message. Follow-up bodies accept `model` and `effort`, including switching between API and ChatGPT plan models.

The workspace uses the same model and effort popovers for tasks, follow-ups and schedules. Message composer controls are ordered attachment, model, effort; selecting a different model resets effort to its default.

## ChatGPT plan sign-in

ChatGPT plan access follows OpenAI's "Sign in with ChatGPT" token sharing for open-source apps. All routes are personal, use the session cookie and origin checks, send `Cache-Control: no-store`, and never return tokens.

- `GET /api/v1/subscriptions` returns `{providers, accounts, pending, welcome}`. Accounts are `{id, provider, email, label, status: "active"|"signed_out"|"reauth", plan: "enabled"|"disabled"|"not_eligible", limited, connected_at, usage_url}`. `pending` is this browser session's sign-in attempt `{provider, account_id, url, expires_at}` or `null`.
- `POST /api/v1/subscriptions/chatgpt/login {account_id?}` starts an attempt bound to the current session and returns the authorize URL. Without `account_id` it registers dynamically (`client_id=dynamic_agent_client`, `agent_name_hint=Gond Agent`); with one it reauthorizes with that account's issued `oaiapp_` client ID, `login_hint`, and `id_token_hint` while a valid ID token is stored. Every request sends the server's persisted `ext_agent_host_id` (`urn:uuid:…`), `redirect_uri=http://127.0.0.1:1455/auth/callback`, scopes `openid profile email offline_access resource.invoke chatgpt.tokens.use.direct`, `resource=https://api.openai.com/v1`, PKCE S256, `state` and `nonce`. A new attempt replaces the session's previous one; attempts expire after 10 minutes.
- `POST /api/v1/subscriptions/chatgpt/callback {url}` completes the attempt from the pasted loopback address. Only an `http://127.0.0.1:1455/auth/callback` address with single-valued parameters is accepted; it is parsed and never requested. A wrong address or stale `state` returns 400 and keeps the attempt for a corrected paste; `error=access_denied`, a mismatched `client_id` on reauthorization, a different ChatGPT account, an ID token that fails JWKS, issuer, audience, expiry or nonce checks, and a used or expired code end the attempt with a plain 4xx/5xx error. The code is exchanged at `/api/accounts/oauth/token` with the same `redirect_uri`. Returns `{account, welcome}`.
- `DELETE /api/v1/subscriptions/chatgpt/login` cancels the session's attempt. `POST /api/v1/subscriptions/welcome` records that the first-sign-in notice was shown.
- `POST /api/v1/subscriptions/accounts/:id/sign-out` revokes the refresh token (`token_type_hint=refresh_token`, retried on server errors), clears tokens and keeps the registration; it returns `{revoked}`. `DELETE /api/v1/subscriptions/accounts/:id` signs out and deletes the account entry.

A sign-in without `chatgpt.tokens.use.direct` is saved with `plan: "disabled"` and offers no models. Models come from `GET https://api.openai.com/v1/models` with the access token, keeping `visibility: "list"` entries, their reasoning levels, context window and image input. Inference uses `POST https://api.openai.com/v1/responses` with `store:false` and `stream:true`, the full history in `input`, `instructions` for the system prompt, function tools grouped in the `gond` namespace (and namespaced replayed calls), and no `previous_response_id`, sampling, `max_output_tokens`, `metadata`, `truncation`, `user`, `background`, `conversation` or hosted tools. Only `response.completed` (or an incomplete response's stop reason) ends a turn; a stream that ends early is a retryable error.

Tokens are sealed with the auth secret in `subscription_accounts`. The API service refreshes an access token five minutes before expiry and once after a 401, then retries the request once. Refreshes are serialized per account; the rotated refresh token, access token, expiry and scopes are replaced in one compare-and-swap update. `invalid_grant`, `refresh_token_reused`, `refresh_token_expired`, `refresh_token_invalidated` and `invalid_client` clear the tokens and mark the account `reauth`. Plan errors map to plain messages and never fall back to an API connection: `subscription_sharing_usage_limit_exceeded` (429, pauses the account's plan requests for a minute, `limited: true`), `subscription_sharing_usage_unavailable` and `subscription_sharing_user_unavailable` (503, retryable), `subscription_sharing_user_not_eligible`, `chatpass_v2_scope_not_authorized` and `chatpass_v2_invalid_authorization_context` (403, `plan: "not_eligible"`, no automatic sign-in loop), `subscription_sharing_unsupported_capability` (400, names `param`), `subscription_sharing_route_not_supported`, and direct-admission 403/503 bodies without a code.

The model relay returns failures to the runner as `{error:{code,message,retryable}}` JSON with the mapped status, for API connections and ChatGPT plans alike. Provider error bodies stay in server logs as status and code only.

## Driving Gond Agent from another bot

Send JSON-RPC MCP `tools/call` requests to `/mcp` using an account-owned bearer token (not cookies). Existing `status` and `phase` fields are unchanged. `get_session`, each entry in `list_sessions`, and `read_session_events` share these additive fields:

| state | Existing status | done | waiting_for_input / asking_question |
| --- | --- | --- | --- |
| queued | queued, or pending follow-up | false | false |
| working | working (including boot/publish) | false | false |
| waiting_for_input | active with an emitted pending question | false | true |
| done | ready, no queued work | true | false |
| failed | failed, no queued work | true | false |
| stopped | stopped, no queued work | true | false |
| merged | merged, no queued work | true | false |

`done` means the current work has ended (successfully or otherwise), not that follow-ups are forbidden. `question` is the pending question text or null; `last_error` is the failed run's last error message or null; `pr_url` is a URL or null. Finishing/pushing is still working, not done. Browser-created and MCP workers may emit a pending question through `ask_user`; questions are optional and do not create a completion gate. Scheduled and other unattended workers return an immediate non-interactive tool result telling the model to proceed with its best judgment, never a pending question. A final response merely phrased as a question is not an input-blocking event. If a worker emits a real pending question, send its answer with `send_session_message`; API-worker answers are routed to that request instead of queued behind the blocked turn.

`read_session_events` accepts `wait_seconds:0..30`. It returns on new events, terminal work, pending input, or the wait deadline, checking persisted state at most every 250 ms even without new events. Result `return_reason` is `done`, `waiting_for_input`, `events`, or `timeout` (in that priority). Read `has_more` and advance `after_seq` to `next_cursor`; large events use `read_session_event`. Completion can be returned alongside unread events: drain remaining pages if the full transcript is needed. Token validity and account ownership are rechecked before returning waited-for data. Disconnecting the client does not stop work.

Runs have no elapsed-time, idle, step, token-total or tool-call budgets. Explicit close/merge/delete and shutdown/recovery clean up containers; successful idle containers do not expire. Failed workspaces have a bounded retention window described below. CPU/memory/PID, archive/frame/body/output sizes, queued-message bounds, MCP traffic and concurrency limits remain resource protections. Bash foreground calls time out after 120 seconds by default (maximum 600 seconds), returning a tool error so the loop continues; long builds can run in the background and be read with `bash_output`. Model requests have no total elapsed-time budget. `MODEL_STALL_MINUTES` (default 10, 0 disables) aborts only after no response headers or body bytes arrive for that interval; each nonempty chunk resets it. Stalls use the existing retryable model-error path; progressing streams are not cut off. Disconnect/cancellation still aborts requests. Control RPCs and Git operations retain per-operation timeouts for unavailable infrastructure. Successful turn publication commits as the run owner's effective GitHub account using one service identity resolver, never a fixed product author. Optional name/email overrides are documented in README.

### Release finished sessions

After reading the result and diff and opening any desired PR, call `close_session` to free the workspace slot and automatically start waiting work. Successful finished sessions do not expire automatically. Stop is non-destructive for healthy live workspaces and does not free a slot; it cancels capacity-queued work instead. Close also cancels capacity-queued work, but refuses while a live turn, pending message or startup is active. For stopped work it snapshots and pushes uncommitted edits first; if snapshot or push fails, the workspace stays open. History and diff remain readable, and a follow-up shallow-clones the pushed branch, queuing if capacity is unavailable. The workspace's More → Close workspace action and `POST /api/v1/runs/:id/close` use the same owner-scoped operation.

Exception for failed kept work: `stop_session` or `close_session` releases it immediately, discarding unpushed work. Send a follow-up first to retry publication if those changes are needed.

### Retry and failure state

Network Git clone/fetch/push and GitHub GET operations retry only network/TLS/timeouts, HTTP 5xx and 429, at most five total attempts with exponential full jitter (1s base, factor 2, 30s cap); Retry-After is a minimum. Non-GET GitHub calls retry only proven pre-send DNS/refused/TLS-handshake/certificate failures or HTTP 429/503 with an explicit valid Retry-After; ambiguous timeout/reset/EOF outcomes never replay writes. Interactive GitHub calls have one 60-second total attempt/wait deadline (`GITHUB_INTERACTIVE_TIMEOUT_MS`), with command timeouts bounded by the remaining budget. Only background publication opts into the full schedule. Other 4xx, authentication failures, rejected/non-fast-forward pushes and unknown failures never retry. Model streams retry identical requests at most three total attempts (1s/2s backoff) before response completion, respecting `retryable:false`; partial attempts cannot execute tools or enter model history. Exhausted dropped streams report `The model connection dropped 3 times`. Downstream cancellation never triggers a retry. The API client alone owns transient backoff; the agent/compaction layer never multiplies that schedule. The shared overflow classifier returns explicit context overflow directly to in-turn compaction, excluding HTTP 429, rate/quota codes and output-token limits. Every actual summary HTTP attempt, including a mid-stream retry, consumes the shared 16-request compaction cap. `stream.reset` remains agent-scoped across compaction: discarded main/summary attempts never enter compacted history, and transcript rollback preserves `compacted` markers and queued user messages.

Publication push integration: `pushBranch(cwd, branch, env, retryOptions?, pushOptions?)` accepts `{lease?: "create-only", beforePush?: ({cwd,branch,head}) => Promise<void>}`; `importBundle(cwd, bundle, branch, env, retryOptions?, pushOptions?)` forwards it. Lease defaults to none. `publicationPushOptions(run, beforePush?)` composes `lease: "create-only"` for explicit branches while `!run.pushed` with the optional policy guard. All three service paths use this helper: initial import, retained push retry and capacity-reclaimed commit republish. Explicitness is persisted, never inferred from the name. For a not-yet-published branch, `pushed` remains false until awaited publication succeeds, including exact-commit reconciliation. A failed `boot()` push preserves that `pushed:false`, `kept_commit` and the clone, so the next boot still uses the create-only lease and guard. Later confirmed pushes omit the lease. All attempts retain the same pinned commit and empty `--force-with-lease=refs/heads/<branch>:` expectation. `stale info` is classified as non-retryable rejection; only in create-only mode may one owner-credential-scoped `git ls-remote --refs origin refs/heads/<branch>` reconcile it to success when the ref equals the pinned commit. Different, missing, malformed or unreadable refs preserve the rejection; never retry without the lease.

A CI-config guard, when present, must be composed through the same helper's `beforePush` argument for every publication path, including direct `pushBranch` recovery calls. It receives the pinned commit and must check that commit plus the current run/PR policy state before each push, not just before bundle import. The hook executes inside the attempt schedule but outside error classification/retry; a refusal propagates unchanged and prevents that push. `beforePush` is wrapped by the retry scheduler's `beforeAttempt` hook; this seam does not itself implement CI policy.

Service lifecycle failures emit an additive transcript event:
```json
{"type":"run.error","step":"push","class":"server","attempts":5,"ts":1234567890,"seq":42}
```
Fixed step labels include `clone`, `fetch`, `github_api`, `snapshot`, `import`, `push`, `model` and `turn`. Classes include `network`, `tls`, `timeout`, `server`, `rate_limit`, `auth`, `client`, `rejected` and `unknown`. No raw diagnostics, URLs or credentials are included. `run.status` follows with status `failed` and a safe message naming the step and attempt count.

`get_session`, `list_sessions` and `read_session_events` retain the string/null `last_error` contract; the message now includes the failing step. Additive `last_error_details` is `{step,class,attempts}` for classified failed runs, otherwise null. `work_kept` is a boolean. A failed run has phase `idle`, done true (unless queued work exists), and retains its workspace and API clone while `work_kept:true`. Retained failures occupy capacity. Follow-ups first retry the previous pending publication, pushing the already-imported commit when available, before sending a new turn.

`GOND_AGENT_FAILED_KEEP_MINUTES` defaults to 60; 0 releases immediately. When a new run, reopened follow-up or queued work needs capacity, idle kept failures can be reclaimed oldest-first, clearing `work_kept` and waiting for container destruction before allocating a replacement. Queued work can reclaim kept failures even before their grace period expires. Worker volumes, uncommitted/unimported work and pending bundles are lost; history/diffs survive. An already-imported commit survives in its API clone (`kept_commit` in stored run data, never a bundle); follow-up republishes it before re-cloning/re-creating the worker. Failed republish preserves the clone for retry; run/account deletion removes it. Snapshot/import failures immediately drop in-memory base64 snapshots and re-snapshot a still-kept worker on follow-up. Expiry or explicitly stopping/closing a still-kept failure discards unpushed work and releases capacity. Successful idle workspaces never expire. Startup recovery still removes disposable workers; absent workspaces reopen the last pushed branch unless a saved capacity-reclaimed commit must first be republished.


## Optional search and bounded tool output

The worker's loopback relay accepts POST `/v1/search` alongside model requests, multiplexed over the existing `model`/`model_id` control frames and `model_cancel` cancellation. The service's worker catalog adds `web_search: boolean`; only true advertises the tool at worker startup. Search credentials never enter the worker. Unconfigured calls fail plainly without falling back. Existing workspaces keep their advertised tools, but every request rechecks configuration.

`web_search` input is `{query,count?}`: 1–1000 characters, default 5/max 10 results. Output contains an untrusted-text warning and `{title,url,snippet}` results. Titles/URLs/snippets are capped at 240/2048/1500 characters; the service limits provider response reads to 1 MiB, rejects redirects and applies a 15-second timeout plus relay cancellation. Brave auth uses a service-held `X-Subscription-Token` header. Errors omit keys and upstream bodies. Admin-only GET/PUT `/api/v1/settings/web-search` exposes provider/key-presence state and accepts replacement `apiKey`/`clearKey`; POST `/api/v1/settings/web-search/test` tests saved settings. Clearing the final account removes the sealed search setting too. SearXNG is not currently supported.

Built-in text results pass through one shared output wrapper (30,000-byte previews). Large results include an ephemeral path under `/tmp/gond-agent-output/` and read offset/limit or grep instructions. Shell producers spill before dropping their head/tail buffers. Files are capped at 32 MiB, total storage at 128 MiB including active reservations; oldest inactive outputs are cleaned first. A cap/busy-store failure is reported as incomplete, with narrowing/paging guidance. Paths include a sanitized call ID and unique suffix to avoid concurrent or batched collisions.

`grep` supports `context_before`/`context_after`/`context`, files/content/count modes and zero-based result-line `offset`/`head_limit` paging; context lines are page rows too. Ordinary reads are streamed, at most 1 MiB per line; optional multiline searches require files no larger than 8 MiB. `bash_output` adds `wait_seconds` (0–120) and `until` (regex over unread buffered output); `bash_list` lists shells. Read-only `git` offers status/diff/log/show/blame. Optional `run_checks` reports exit_code (null for timeout/interruption), duration_seconds, summary, detected failures and an output tail; background calls return bash shell IDs. None changes completion behavior. All images use the shared worker image limits described above; `web_fetch` remains text-only and rejects raster responses.

## Task plan state

`update_plan {plan:[{step,status}],explanation?}` replaces the main worker's plan; `list_plan {}` reads it. Statuses are `pending`, `in_progress`, `done`. Multi-step tasks should begin with a plan, keep one step in progress while working, and update statuses as work changes. Plans are bounded to 50 steps and 300 characters per text. `todos {agent_id:"main",items:[{text,status}]}` events replace the displayed plan and persisted summary; subagent plans do not change it.

`get_session`, `list_sessions` entries and `read_session_events` share additive fields:
- `plan_steps`: up to 50 `{text,status}` entries, text limited to 300 characters.
- `plan_done`, `plan_total`: counts over those bounded entries.
- `current_step`: `{text,index}` for the first `in_progress` step (1-based), or `null`.

No plan returns `[]`, `0`, `0`, `null`. These fields are independent of session completion: `done:true` is valid with unfinished plan steps.

Example JSON inside MCP text content:
```json
{"id":"run_example","state":"working","done":false,"plan_steps":[{"text":"Inspect code","status":"done"},{"text":"Implement change","status":"in_progress"},{"text":"Run checks","status":"pending"}],"plan_done":1,"plan_total":3,"current_step":{"text":"Implement change","index":2}}
```

The API folds plan snapshots into durable run summaries and reconstructs older summaries from the latest stored main `todos` event. The restore result, including an empty plan when there are no Todos events, is saved once without changing run timestamps; subsequent reads skip the event lookup. Follow-ups preserve them. Controller `start` accepts optional `plan` plus `plan_reminder_every` and `plan_nudge_limit`, forwarded as `GOND_AGENT_INITIAL_PLAN`, `GOND_AGENT_PLAN_REMINDER_EVERY` and `GOND_AGENT_PLAN_NUDGE_LIMIT` to the runner. Reopened containers receive the stored plan, including after service recovery; this does not restore lost filesystem changes or the complete model history.

Reminders are main-loop request context, not transcript events or provider-specific behavior. The interval counts main model rounds, resets per user turn, defaults to 6, and 0 disables reminders including change-triggered ones. With reminders enabled the first request and the request immediately after a plan change include current statuses. Pending/in-progress steps may trigger at most two continuation nudges per user turn (configurable down to 0). The counter never resets on plan edits or tool calls. Exhausting nudges ends normally on the next final response, without checking plan completion. Interrupted/error paths do not trigger nudges. No review/completion gate exists.

Invalid initial-plan JSON is ignored with a warning and an empty plan, never a startup error. Service plan controls accept only nonnegative decimal integers through the u32 range; invalid settings warn without echoing values and use defaults. Compose forwards both controls from `.env`. Nudge wording is singular for one step ("1 plan step is still pending") and plural otherwise ("N plan steps are still pending").

Worker `start` accepts `interactive: boolean`. The service sets it true only for `source: web` and `source: mcp`, false for scheduled `source: runner` and all other sources. The controller sets `GOND_AGENT_INTERACTIVE` to true only for the literal boolean true; omission defaults to false. The runner enables questions only for the literal environment value `true`. This startup choice is preserved across follow-ups and recomputed from the stored source when reopening a workspace.

`GOND_AGENT_WEB_SEARCH_LIMIT` caps service-side web search attempts per run (default 30, 0 unlimited). It accepts only unsigned decimal integers through u32; invalid values warn without echoing the value and use 30. Compose exposes the setting in `.env.example`. Attempts, including errors/cancellations, are counted and saved in SQLite before provider work; the count is shared across concurrent calls, follow-ups, worker reopen and service restart. A limit response says "web search limit for this run reached" as a tool error, never a failed run. Settings connection tests are not run calls and do not consume a run's allowance.

Interactive browser/MCP questions wait at most `GOND_AGENT_QUESTION_WAIT_MINUTES` (default 240 minutes / 4 hours; 0 waits indefinitely). This is only a wait-for-a-human/bot timeout, **not a run time budget**: expiry returns "No one answered; decide yourself and continue" and the same run continues. Answers before expiry still resume normally. The service validates unsigned decimal u32 integers (invalid values warn without echoing them and use 240), reads the setting and passes `question_wait_minutes` at worker start; Compose and `.env.example` expose it. A matching `question.resolved {request_id,agent_id}` event clears pending input on answer or timeout, returning MCP state from `waiting_for_input` to `working` before the turn ends. Scheduled runs remain non-interactive and never wait at all.
